Students and parents have portals of their own inside their school's address. This page covers what each can do, how parents are linked to children, and, importantly, how the platform tells parents things.

The student portal

Code: {{ file('blueprints/student_portal/routes.py') }} and {{ file('blueprints/student_portal/helpers.py') }}. A student signs in at the school's /login and lands on their dashboard ({{ route('student_dashboard') }}):

  • Assignments and projects set for them, and CBT quiz assignments they can take.
  • Tests and examinations for their class and current session; one attempt each, timed, with answers saved as they go.
  • Practice, always open and retakeable; see {{ page('academics', 'Academics') }}.
  • Results, only once released, and their report cards once a term is complete ({{ file('blueprints/student_portal/report_cards.py') }}).
  • Notifications, and a password change. A student on a temporary password is forced to change it first (student_required).

Every route that takes a student id from the address checks it against the signed-in session; there is no way to open another student's page by editing a number.

The parent portal

Code: {{ file('blueprints/parents/routes.py') }}, helpers in {{ file('blueprints/parents/helpers.py') }}, report cards in {{ file('blueprints/parents/report_cards.py') }}. A parent account ({{ table('parent_accounts') }}) is linked to one or more children through {{ table('parent_student_links') }}; a link can be switched off. The link, not the account, authorises everything: a parent can open a child, the child's finances and receipts, and the child's report cards only through an active link ({{ route('parent_dashboard') }}, {{ route('parent_child_detail') }}, {{ route('parent_child_finance') }}).

  • Parents follow results (once released), attendance and fee status, download receipts as PDF, and read report cards.
  • Feedback is a two-way thread between a parent and the school ({{ table('parent_feedback') }}, {{ table('parent_feedback_replies') }}) with optional attachments (served only by a permission-checked download). Staff triage and reply from the admin side; who may is parent.feedback.view and parent.feedback.manage.
  • Staff create parent accounts (and link them to students), each with a one-time password. A brother or sister is linked to the same parent account, not a new one.

Email and SMS: a school's own accounts

What parents receive (receipts, password-recovery emails, alerts) is sent from the school's own accounts, so a parent sees the school, not the platform. Code and rules: {{ file('core/delivery.py') }}. The school's own top-level administrator sets them up on Email & SMS ({{ route('admin_school_delivery') }}) - restricted to that one admin type, not a permission any other role can be granted - each with a button to test before relying on it.

RuleWhy
The platform's shared account is the fallback. A school that has set up nothing sends through the BRIGHTSTARS_SMTP_* / BRIGHTSTARS_SMS_* account if the deployment has one. With neither, it cannot send, and says so.New schools work at once, but nothing is ever sent from a place nobody chose.
A half-set-up school never borrows the platform's account. Once a mail host is entered, the school's settings are used exclusively, even if incomplete.Otherwise a typo would quietly send a school's parents' mail from the platform's address.
Secrets are encrypted at rest (Fernet) in the school's own database, under a key derived from the application secret and the school's code. Never shown again; blank on save means "keep".A copy of a school's database is not a copy of its mail credentials, and one school's stored token means nothing in another. Set BRIGHTSTARS_DELIVERY_KEY so rotating the app secret does not strand them.
The server cannot be aimed at its own network. In production a school's mail host must resolve only to public addresses (checked when saved and again before each connection, connecting to the very address checked); only ports 25, 465, 587 and 2525.A school chooses a host the server connects to, which is a way to probe internal services.

What parents are told, and when

EventChannelsCode
New assignment or projectin-app, email to the guardian_notify_guardians_of_school_work
A fee charged to their childin-app, email, SMS_notify_parents_fee_assessed
A payment recordedin-app; the receipt PDF by email and a payment text by SMS, automatically_notify_parents_payment_recorded, _send_payment_receipt_to_guardian
A term's results released, so the report card is readyin-app, email, SMS_notify_parents_report_card_ready, {{ file('blueprints/school/result_notices.py') }}

All in {{ file('core/notifications.py') }}. They share one contract: best effort, and never blocks the change that triggered it. A missing channel, an unset contact or a failed delivery for one child never stops the others and never rolls anything back. Each sender is called only after its own commit has succeeded.

Every attempt through the two guardian-contact senders (_notify_guardian_email, _notify_guardian_sms) is also recorded to {{ table('notification_delivery_logs') }} - student, kind, channel, recipient, sent or failed, and why - so a school can answer "did she get it?" itself from {{ route('admin_notification_log') }} ({{ file('blueprints/school/notice_log.py') }}), without asking a developer to read a server log. Payment receipts keep their own, older version of this ({{ table('finance_delivery_logs') }}).

Because delivery can be slow, the payment receipt and the report card notices are sent as a durable background job ({{ file('core/jobs.py') }}), so a restart mid-send is retried rather than lost. The in-app alerts are written synchronously so they are there when the page reloads.

Idempotence. The report card notice fires when a term becomes complete, and only then: releasing one subject of several says nothing (the term is not ready yet), and releasing the last one sends it. If a result is later edited and the term released again, the parents are told again; that is a real new event.

Archived children and family notices

Archiving a student stops that student's sign-in, and nothing else. Their parents still see the child on the parent portal, with the record and the fee account, because the parent's link to the child is kept and the portal includes archived children. The portal's own queries say so explicitly, so a future change to the student filter does not hide them by accident.

Parents and students each get a what's-new notice, written for their own audience, on their own dashboard. It never links to the staff guide. See {{ file('blueprints/family_notices.py') }}.

Password recovery

{{ route('forgot_password') }} accepts an identifier for any of the four account types, finds the account and emails a single-use link ({{ table('password_reset_tokens') }}; only a hash of the token is stored). The reset pages are never cached and send no referrer, so a link is not kept or shown to anyone. Using a link ends the account's other sign-ins. Requests are rate limited per address and username.
