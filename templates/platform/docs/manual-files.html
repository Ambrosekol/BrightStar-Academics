A school's files are its uploads (logo and sign-in photographs, staff and student photographs, signatures, question and assignment pictures, store pictures, message attachments), its question banks, and its numbering rules. They live either in a folder per school (BRIGHTSTARS_STORAGE_BACKEND=local, under BRIGHTSTARS_TENANTS_DIR, tenants/<code>/ by default) or in an S3-compatible bucket (s3). All reading and writing goes through {{ file('core/storage.py') }}, so the rest of the code works the same either way.

Pictures and files not showing

A picture shows as broken, or a file link answers "Page not found"

You see
A broken-image icon, or a 404 when opening /static/uploads/….
Why

Uploaded files are not open to everyone: each folder has a rule ({{ file('core/upload_access.py') }}), and a refusal is a plain 404 so it never confirms a file exists. Also, the file may really be missing.

FolderWho may open it
branding/anyone (the sign-in page needs the logo and photographs)
messages/never here; only the permission-checked attachment download
admins/, signatures/staff
candidates/staff, and the candidate the photograph belongs to
students/staff, the student, and a parent linked to them
questions/staff, students and candidates
assignments/staff and students
store/staff and parents
anything elsestaff
Fix
  1. If the person should not see it (for example a parent opening another family's photograph), the 404 is correct.
  2. If they should: are they signed in to this school, and still signed in? A sign-in that has ended opens nothing.
  3. Is the file there? Local: ls tenants/CODE/uploads/<folder>/. S3: the log says "uploads/… is named by the database but is not in object storage" when it is missing.
  4. If it is missing, upload it again (a moved server whose tenants/ folder was not copied loses every file: copy it across).
Check
The picture shows for the right people.

Pictures fail only on S3: "Could not read uploads/… from object storage"

You see
Broken pictures everywhere; the log says "Could not read uploads/… from object storage" with the provider's error.
Why

The bucket refused or failed the read: keys without read permission, the wrong region or endpoint, a renamed bucket, or a network fault ({{ file('core/object_store.py') }}).

Fix
  1. Check BRIGHTSTARS_S3_BUCKET, BRIGHTSTARS_S3_ENDPOINT_URL (needed for anything that is not AWS) and BRIGHTSTARS_S3_REGION (often auto for R2).
  2. The key needs read, write, list and delete on the bucket (and the prefix, if BRIGHTSTARS_S3_PREFIX is set).
  3. Test from the server: aws s3 ls s3://BUCKET/ --endpoint-url URL with the same keys.
Check
A school's logo shows on its sign-in page; uploading a new photograph works.

Files appear on one server but not the other

You see
A photograph uploaded a moment ago is broken for some people, fine for others.
Why

Two or more application servers use local storage, each with its own folder: a file saved on one is not on the other.

Fix

Use BRIGHTSTARS_STORAGE_BACKEND=s3 (recommended), or put BRIGHTSTARS_TENANTS_DIR on shared storage every server mounts. Copy the files already uploaded into the shared place.

Check
A new upload shows on every server.

Uploads refused

"… is … The limit is … Choose a smaller picture"

You see
"photo.jpg" is … The limit is … Choose a smaller picture, or reduce this one first.
Why

A single picture may be up to BRIGHTSTARS_MAX_UPLOAD_BYTES (5 MB by default); a whole form up to BRIGHTSTARS_MAX_REQUEST_BYTES (8 MB); a bulk-import file up to BRIGHTSTARS_MAX_DATA_UPLOAD_BYTES (2 MB). Every file box prints its limit and refuses a too-large file before anything is sent ({{ file('core/uploads.py') }}).

Fix

Make the picture smaller (any phone's "share as medium size", or an online resizer). Raise the limits only if schools genuinely need it, and raise your proxy's limit to match (nginx client_max_body_size).

Check
The picture uploads.

"… is not a picture we can use" / "does not appear to be a valid image"

You see
"scan.pdf" is not a picture we can use. Please choose a PNG, JPG, GIF or WEBP image. — or — … does not appear to be a valid image. It may be another kind of file that was renamed, or a damaged picture.
Why

Only PNG, JPG, GIF and WEBP are accepted, and the file is opened and re-drawn to be sure (a renamed PDF or a damaged file fails). HEIC photos from iPhones are not accepted.

Fix

Save or export the picture as JPG or PNG (on an iPhone: Settings › Camera › Formats › Most Compatible, or share it as JPG).

Check
The picture uploads.

"The file you sent is larger than the limit … for one submission"

You see
The page you came from, with this message at the top (HTTP 413).
Why

The whole submission was over BRIGHTSTARS_MAX_REQUEST_BYTES (several large photographs at once, usually). It is refused before anything is saved ({{ file('core/request_errors.py') }}).

Fix

Send fewer or smaller pictures at a time.

Check
The form saves.

Bulk imports (students, history, past results)

Each of the three steps takes a CSV or an Excel workbook (.xlsx), read by {{ file('core/tabular.py') }}. A file-level problem refuses the whole file before anything is written; a row-level problem skips that row with its line number and reason, and every good row is still imported.

"The file is missing required columns: …" or "That file has no header row"

You see
The file is missing required columns: guardian_email, guardian_phone. — or — That file has no header row. Use the template.
Why

The first row must be the column names, spelled as in the template (case and spaces around them do not matter).

Fix

Download the step's template, paste the data under its header row, and upload again. For students every column is required: first_name, middle_name, last_name, gender, class, guardian_name, guardian_email, guardian_phone.

Check
The report shows imported and skipped rows.

"That file is not readable as plain-text CSV"

You see
That file is not readable as plain-text CSV. Save it as CSV (UTF-8) or as an Excel workbook (.xlsx) and try again.
Why

The file is not UTF-8 text (an old "CSV (MS-DOS)" save, or a file in another encoding).

Fix

Upload the Excel workbook itself (.xlsx), or in Excel use Save As › CSV UTF-8 (Comma delimited).

Check
The import runs.

An Excel file is refused

You see
One of: "Only plain Excel workbooks (.xlsx) and CSV files can be imported." · "That workbook contains macros." · "That Excel file is password-protected." · "That Excel file unpacks to far more than an import needs." · "That file is not an Excel workbook (.xlsx)." · "That Excel file could not be read." · "Excel files cannot be read (safely) on this server yet."
Why

Uploaded workbooks are read defensively: macro-enabled (.xlsm), old .xls, password-protected and oversized files are refused; the workbook's XML is parsed safely (any trick inside it makes it "could not be read"); formulas are never run. The last message means the server lacks openpyxl/defusedxml.

Fix
  • Open the file in Excel or Google Sheets and save it as a plain .xlsx (or CSV), with no password.
  • "cannot be read on this server yet": on the server, pip install -r requirements.txt and restart.
Check
The import runs.

Rows from Excel come through empty, or are skipped for a missing name

You see
Rows built with formulas (for example =CONCAT(A2," ",B2)) arrive empty and are skipped.
Why

Formulas are never run on the server; the value Excel last saved is used. A workbook made by a program that never calculated it has no saved values.

Fix

Open the workbook in Excel and save it once (that stores the values), or copy the column and Paste Special › Values before uploading.

Check
The rows import.

Rows are skipped with a reason

You see
The report lists skipped rows by line number: missing first name, a gender that is not Male/Female, an unknown class, a class outside your scope, a bad guardian email, a session that does not exist…
Why

Each row is checked exactly as registering one by hand would be. A teacher limited to some classes can only import into those.

Fix

Correct only the skipped rows and import a file of just those. The past-results step never overwrites a result already on record, but importing the students step twice would create every student twice, so never re-send rows that were already imported.

Check
The report shows them imported.

Question banks and numbering files

A question bank file is refused

You see
"The file is not valid JSON. Check it for a missing comma, quote or bracket." · "The file is too big…" · "A bank with the id … already exists here." · a list of problems with individual questions.
Why

Imported banks are checked strictly ({{ file('core/banks.py') }}): one JSON object, at most 2 MB, a safe id and a name, 1 to 500 questions each with four different options and an answer, no picture paths. Every problem is listed at once.

Fix

Fix each listed problem (a JSON validator such as jsonlint.com shows where the syntax breaks). To replace an existing bank, tick Replace it (needs the edit permission).

Check
The bank appears in the school's list.

Registering a candidate shows a numbering error

You see
A plain message about the school's numbering rules on the candidate form; codes cannot be issued.
Why

The school's numbering.json is unreadable (edited by hand, a disk fault). It is never silently replaced, so no code is issued from a guess ({{ file('core/numbering.py') }}).

Fix

Open the school's page in the console, go to Numbering, check the patterns (the preview shows the next codes), and save. The save replaces the file and keeps a copy of the broken one.

Check
The preview shows sensible next codes; registering a candidate works.
