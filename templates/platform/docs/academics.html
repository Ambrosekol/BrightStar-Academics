Academics is the day-to-day teaching side of a school: who is enrolled where, what work is set, how it is marked, how marks become a term result, and when parents and students may see it. Most of the code is in {{ file('blueprints/school/routes.py') }} (routes) and {{ file('blueprints/school/helpers.py') }} (rules), with the term arithmetic and report card rules in {{ file('blueprints/school/report_card_data.py') }}.

Class subdivisions and class transfers

A large JSS or SSS class can be split into subdivisions (JSS 1A, JSS 2 Gold, SS 1A Science), each with its own class teacher. The rules live in {{ file('core/subdivisions.py') }}; the School Admin's Settings page is {{ route('admin_school_subdivisions') }} ({{ file('blueprints/school/subdivisions.py') }}).

  • Inside the class, not a class of its own. The class stays one class for its subjects, subject teachers, timetable, fees, results and class averages. A subdivision only scopes its class teacher's own work: the register, report card comments and trait ratings, and releasing results. An SSS subdivision may carry a department; it then takes only students of that department (a subdivision with none takes anyone).
  • Placing students in turn. A student goes to the eligible subdivision with the fewest students this session, the earlier one on a tie (choose). This happens in one place, a SQLAlchemy before_flush listener (_place_on_flush): a new enrolment, an enrolment moved to another class, or a student whose department changed to one their subdivision does not take. So registering a student by hand, a bulk import, an entrance admission and promotion all place students without any of them knowing about subdivisions. An enrolment whose subdivision_id is set explicitly in the same save is left as set. Splitting a class (or removing a subdivision) spreads the class's unplaced students with spread; removing every subdivision clears them all.
  • The lock. Once set up, the School Admin locks the set-up (a key in {{ table('school_settings') }}, class_subdivisions_locked); nothing can be added, renamed or removed until it is unlocked. Moving a student is still possible, by transfer.
  • Class teachers per subdivision. A class-teacher duty may name a subdivision (teaching_duties.subdivision_id, given on the staff form and the Teachers page). teacher_subdivisions returns the subdivisions a person is limited to in a class, or None when they are not limited (the School Admin, a head teacher, the whole class's class teacher, any subject teacher there). Every class-teacher check (class_teacher_of, _class_teacher_allowed) still passes for them; the student lists are what narrow: the student list and a student's page, the register (class_roster), report card comments and traits, releasing results (_students_taught in {{ file('blueprints/school/results_records.py') }}), and their class card on the Overview. current_limit is the same question for whoever is signed in.
  • Transfers. {{ route('admin_school_transfers') }} ({{ file('blueprints/school/transfers.py') }}, {{ table('class_transfers') }}): the class teacher of a student's subdivision asks to move them to another subdivision, or in SSS another department (and so a subdivision that takes it). Nothing changes until it is approved by the class teacher of the subdivision they would join (approvers), or by the School Admin or a head teacher, who may decide any transfer. Nobody approves their own request, so a transfer nobody else can approve (into a subdivision with no class teacher, or a department change in a class without subdivisions) waits for the School Admin or a head teacher. One pending transfer per student; approving applies it with apply_transfer, which sets the department first and the subdivision last, so the placing listener keeps the chosen subdivision.

Bulk student import

A school with existing students does not type them in one at a time: {{ route('admin_school_students_import') }} takes a CSV — first_name, last_name, gender and class required; middle_name, guardian_name, guardian_email, guardian_phone optional ({{ file('blueprints/school/student_import.py') }}) — and creates, for each valid row, exactly what "Register Student" creates by hand: the student record, an enrolment in the named class for the current session, and a login with a generated admission number and a one-time password, through the very same numbering ({{ file('services/student_number_generator.py') }}) and account machinery (_provision_student_account in {{ file('app.py') }}) either way. class is matched against the school's own class names case-insensitively, and is checked against the importing staff member's own scope like any other student action. A row that fails is skipped with a reason by line number; every other row in the file is still tried, and each valid row is committed on its own, so one bad line never holds back the rest. The generated usernames and passwords are shown once, on the results page, and never stored in plain text; downloading them as a CSV happens in the browser, from that same page, never a second trip to the server. A file with no header row, a missing required column, or one over the upload's own size limit (upload_attrs('data'), {{ file('core/uploads.py') }}) is refused outright, before a single row is read.

Bulk enrolment-history import

The importer above only ever creates a student's current record - the deeper migration a school moving from another system usually still needs is its students' past classes and sessions. {{ route('admin_school_students_import_history') }} ({{ file('blueprints/school/student_history_import.py') }}) takes a second CSV - admission_no, level, session required; enrolled_at, completed_at, notes optional - matched to an already-active student by admission number, and a session by name. Each valid row does exactly what the single "Add enrolment history" form ({{ route('admin_school_student_history_add') }}) does by hand, reusing its own helpers (_mark_latest_history_current, _sync_enrolment_for_history in {{ file('blueprints/school/helpers.py') }}) so a bulk-imported entry cannot drift from one typed in one at a time - except that a session named in this file need not be the school's currently active one, deliberately: the hand-entry form's own dropdown only offers active sessions, since it is built for everyday correction, while backfilling an archived session is precisely what this importer is for.

How a CBT test or exam is run

  1. A teacher creates the assessment, adds questions (each with four options and a correct one), and opens it. question_count is kept in step with the questions by _resync_question_count.
  2. A student presses Start ({{ route('student_assessment_start') }}). One row is created in {{ table('school_assessment_attempts') }} with an expiry time, and every question is copied into {{ table('school_assessment_attempt_questions') }}. There is at most one attempt per student per assessment (a unique constraint).
  3. Each answer is saved the moment it is chosen ({{ route('student_assessment_answer') }}), as an upsert on {{ table('school_assessment_answers') }}.
  4. Grading reads only the frozen copy ({{ file('blueprints/student_portal/helpers.py') }}, student_assessment_grade), never the live bank, and is idempotent: it only acts on an attempt still active, so two simultaneous submissions cannot both post a result.
  5. The attempt result creates a row in {{ table('school_student_results') }} with status entered.

The copy exists so editing a question later cannot change an exam already taken, and so grading is reproducible. Timing is enforced on the server from the stored expiry, never trusted from the browser's clock.

Theory questions and marking

{{ table('school_questions') }} has question_type (objective or theory) and marking_guide. A theory question keeps blank options and correct_option = -1; its points are its marks. Practice tests refuse theory. The scoring is {{ file('core/theory_marking.py') }}; the teacher's pages are {{ file('blueprints/school/marking.py') }}.

  • Taking. The frozen copy carries question_type but never the guide. A written answer is {{ table('school_assessment_answers') }}.answer_text (at most 5,000 characters), saved by the same answer route with autosave=1 (JSON) as the student types, on leaving the page and before the clock ends.
  • Submitting. student_assessment_grade marks the objective questions only, sets the attempt's theory_status to pending and calls sync_result, which writes the result with score = NULL. A NULL score is left out of the term sums, refused by the result workflow and by _submittable, and keeps the report card from being ready; the result list shows Awaiting marking and the hand-edit form sends it to marking instead.
  • Marking. {{ route('admin_school_marking') }} and {{ route('admin_school_marking_paper') }} need the edit permission of the paper's type ({{ perm('school.tests.edit') }} or {{ perm('school.examinations.edit') }}) and _school_pair_allowed; each student is checked with _student_subject_allowed (SSS departments). They are not in ADMIN_ENDPOINT_PERMISSIONS: each route checks for itself and logs a refusal. {{ route('admin_school_marking_save') }} stores awarded, the comment, who and when, then sync_result fills the score once nothing is pending.
  • The split. {{ table('school_assessments') }}.objective_marks and theory_marks ({{ route('admin_school_marking_split') }}); blank means each part keeps its raw marks. Each part is scaled to its share: objective/objective_raw × objective_marks + theory/theory_raw × theory_marks. Changing it re-scores every finished attempt (refresh_paper).
  • Locks. A released result is never re-scored and its marks are refused; the split is refused once any result of the paper is released. A score that changes on a verified or approved result returns it to entered with a {{ table('result_workflow_events') }} row.

Practice tests

Practice is a self-study bank for students who want to prepare. It is deliberately outside the record:

  • A student finds their class's practice tests under Practice, in every session, and can take and retake them without limit.
  • Each run serves the questions in a fresh random order (up to 40 drawn from the bank), timed like a CBT paper, marked at once, with the correct answers shown ({{ route('student_practice_take') }}).
  • Nothing is written to the database. No attempt, no answers, no result. The chosen question ids live only in the student's session cookie until they submit. So a practice run can never reach a term result or a report card.
  • The old graded start route redirects to the practice page, and results of practice tests made by earlier versions are ignored everywhere a result is counted.

From marks to a term result

A subject's term result is Exam (out of 60) + Continuous Assessment (out of 40) = 100. CA is built from three kinds of work, each scaled to its share; by default a school's weights are test 20, assignment 10, project 10 and can be changed on the sessions page (_ca_weights).

  • Several items of one kind (two tests) are combined by summing their raw score and raw maximum, then scaling the total to that kind's share, never by simply adding them. So an extra test can never push a subject past 100.
  • The rules for what counts are written in one place: _term_raw_sums in {{ file('blueprints/school/helpers.py') }}. Practice tests never count. Removed work does not count. A mark on work with no maximum does not count. A blank mark does not count.
  • Marks are stored as decimals ({{ file('core/marks.py') }}); a whole mark is shown as a whole number ("75 / 100", not "75.0 / 100.0").
  • A teacher can also enter offline results (a paper Test and Exam) by hand; these follow the same workflow.

The result workflow

entered→verified→approved→released

Each step needs its own permission ({{ perm('school.results.enter') }}, {{ perm('school.results.verify') }}, {{ perm('school.results.approve') }}, {{ perm('school.results.release') }}), so different people can do each. The steps are strictly ordered and every move is recorded in {{ table('result_workflow_events') }}. Editing a result sends it back to entered; approved or released results cannot be edited casually. A student sees only released marks. The admin's own term-results table shows every recorded mark whatever its stage (a deliberate decision, called "Option A").

Releasing. Three ways, all ending in the same state:

  1. One result at a time ({{ route('admin_school_result_workflow') }}).
  2. The whole term for one student at once ({{ route('admin_school_results_release_term') }}): in Results & Records, choose a class, search and choose a student, choose a session and term, then press Release all results for this term and confirm. It releases every approved result of that term; results not yet approved stay private. The page and its steps are in {{ file('blueprints/school/results_records.py') }}.
  3. By date: an academic session's result_release_at. When it passes, _release_due_school_results ({{ file('app.py') }}) releases every approved result of that session the next time anyone asks, whichever page it is.

Exam and test timetables

Staff build a timetable as a draft — one entry per class, subject, date and time, with an optional venue ({{ file('blueprints/school/timetable_data.py') }}, {{ table('exam_timetable_entries') }}) — under {{ route('admin_school_timetable') }}, editing and deleting freely; nothing outside staff sees a draft. Releasing the whole session-and-term timetable at once ({{ route('admin_school_timetable_release') }}) sets every not-yet-released entry as released and, on a background thread, notifies every currently enrolled student of the classes it covers and their parents ({{ file('blueprints/school/timetable_notices.py') }}): an in-app alert each, plus an email and a text message to the guardian contact, the same "must not block the request, must never undo what was just saved, must not be lost if the thread sending it never finishes" contract {{ file('core/jobs.py') }} gives every notice like it. Releasing again releases nothing more. Three permissions: school.timetable.view (read-only), school.timetable.manage (add/edit/delete), school.timetable.release (the sensitive one). A student and a linked parent see only released entries for their own class, and can download a PDF ({{ file('core/timetable_pdf.py') }}) or print it.

Attendance

A class teacher ({{ route('admin_school_attendance') }}) takes the register for one class on one date: present, late, absent or excused for each enrolled student, or left blank for "not yet marked" ({{ file('blueprints/school/attendance_data.py') }}, {{ table('attendance_records') }}). One row per student per day, never per subject. Saving the same statuses again changes nothing and keeps the original marker's name; changing a status re-attributes the row to whoever changed it, the same "last honest edit wins" rule report card comments use. A term summary ({{ route('admin_school_attendance_summary') }}) totals present/late/absent/excused and a percentage (late counts as present) for a class, needing only school.attendance.view; taking the register itself needs school.attendance.mark. A student and a linked parent each see their own summary and day-by-day history for a chosen term (/student/attendance, /parent/children/<id>/attendance).

Report cards

A report card is worked out when asked for, never stored, so it can never disagree with the results ({{ file('blueprints/school/report_card_data.py') }}). It is ready for a student and a term the moment every official result of that student in that term is released; one result still waiting holds it back. It shows the school's logo, name, motto and colours; the student's details; each subject as CA plus Exam with a grade and remark (A 70 to 100 Excellent, B 60, C 50, D 45, E 40, F below); the overall percentage; the class average; affective and psychomotor trait ratings, once rated; the class teacher's comment with that teacher's own signature; and the head's title, name and signature. It is drawn as a page and as a PDF ({{ file('core/report_card_pdf.py') }}) from the same data, so they say the same thing.

Who sees them: staff with report_cards.view (limited to the classes they may access), the student, and a parent (through their active link to the child). Comments, traits and staff signatures need report_cards.comment; the head's details need report_cards.manage.

Affective and psychomotor traits. The class teacher rates a fixed catalogue of traits — punctuality, honesty, neatness and the like under Affective Domain; handwriting, sports, drawing and the like under Psychomotor Domain ({{ route('admin_school_report_card_traits') }}) — on a five-point scale (Excellent to Poor), the same page and permission as the comment. A rating is stored as a small JSON object, one row per student per term ({{ table('report_card_traits') }}); a trait left unrated simply is not in it. A student's card shows this section only once at least one trait has been rated, so a school that never uses the feature sees no change to its cards at all.

Telling the parents

When a student's last result for a term is released, by any of the three ways above, the parents are told, once, by email, SMS and an in-app alert that the report card is ready ({{ file('blueprints/school/result_notices.py') }}). Only cards that are actually complete are announced, so releasing one subject of several says nothing. The messages go out on a background thread. Delivery is described in {{ page('families', 'Students, parents and messages') }}.

Promotion between sessions

At the end of a session a school promotes students. A run ({{ table('academic_promotion_runs') }}) lists each student with a decision (promote, repeat, transfer, graduate, withdraw, hold) and a target class from the school's configured progressions ({{ table('school_class_progressions') }}); items are in {{ table('academic_promotion_items') }}. Validation before applying is in _promotion_validate_run. It creates the next session's enrolments and keeps the enrolment history.

Every promotion action - starting a draft, editing it, approving and committing it, and the progression rules it drafts from - is restricted to the school's own top-level admin type (is_school_admin), the same gate {{ route('admin_school_sessions') }} uses: it moves every currently enrolled student at once, including graduating and withdrawing them, so it is kept out of {{ perm('admin.access') }}'s ordinary reach rather than made a grantable permission a custom role could pick up. Promotion appears in the navigation rail only for that same admin type.

Things that have bitten people

  • A PostgreSQL query that selects an expression and groups by it must use the same expression object in both places. Building it twice creates two different bind parameters and PostgreSQL reports a grouping error. See term_of in {{ file('blueprints/school/results_records.py') }}.
  • Never grade from the live bank. Always from the frozen attempt questions.
  • A term is a string. "Full Session" is a valid term for annual results; code that assumes only three terms is wrong.
  • A new list of a class's students for a class teacher's own work must ask {{ file('core/subdivisions.py') }} (current_limit or teacher_subdivisions), or the class teacher of JSS 1A sees all of JSS 1. Do not narrow class-wide figures (averages, positions): results are the whole class's.
