Advice from the people who built it, ordered roughly by how much each item protects you. None of it is a known fault: the codebase's "Known gaps" list is empty. These are things we would do next, and things to watch as the platform grows.

Before the first paying school

  1. Run the whole verification suite against staging with production-like settings ({{ page('testing', 'Testing') }}). Especially the multi-school isolation script.
  2. Set up backups and test a restore of one school into a scratch server. A backup you have never restored is a hope.
  3. Add two-factor authentication for platform admins. A platform admin can enter any school. Their sign-in is the most valuable credential in the company.
  4. Decide the email and WhatsApp story. Either give every school its own sender (recommended: parents recognise the school) or run a shared platform sender. For WhatsApp, apply for approved message templates so notices can reach parents outside the 24-hour window; today the application sends free-form messages only.
  5. Have a teacher of each subject review the standard question banks before a school relies on them for real admissions decisions.

Hardening

  • Separate database roles per school. Today one role connects to every database. Create a role per school and store its URL as env:VARIABLE_NAME in the registry row (supported) so a compromised worker context is limited to one school's data.
  • Tighten the Content-Security-Policy by moving inline scripts to files or adding nonces, then dropping 'unsafe-inline' for scripts.
  • A dedicated poller for background jobs. {{ file('core/jobs.py') }} is now durable (a {{ table('background_jobs') }} row survives a restart and is retried) but self-heals only opportunistically, the next time something of the same kind is enqueued. When volume grows, or an operator wants to see "queued / failed / done" across every school at once regardless of traffic, add a small poller against the same table rather than a new mechanism.
  • Alerting on the log lines that signal degraded safety (registry unreachable, a refused-delivery burst, a sign-in refusal streak, a job that has used up its retries).
  • Rotate the platform secrets on a calendar (with BRIGHTSTARS_DELIVERY_KEY already independent, rotating the session secret costs only a sign-out).

Product recommendations

  • Offer parents a "notify me" choice (channels and quiet hours). Today every parent with a contact on file gets every notice.
  • A notice log per school ("this report card notice went to these parents on these channels") so a school can answer "did she get it?" without asking a developer. Receipts already have this ({{ table('finance_delivery_logs') }}).
  • Bulk release with a preview for a whole class, to complement the per-student release button.
  • Data export for a school leaving: a supported "give me everything" (database dump plus folder) with documentation, which the per-school layout makes straightforward.
  • A refund for an online payment. Paystack's POST /refund is not called anywhere yet — today, undoing a Paystack payment means voiding the {{ table('finance_payments') }} row here and refunding the parent outside the system, by hand, from the Paystack dashboard. A real refund button would call that endpoint from {{ file('core/payments.py') }}, record it, and listen for the refund.processed/refund.failed webhook events (already reaching {{ route('paystack_webhook') }}, just not read yet) to know how it turned out.

How to keep the codebase healthy

  • Every write route gets a real submission in the PostgreSQL script ({{ page('testing', 'Testing') }}). The guard enforces it; do not work around it by listing a route as exempt without a reason.
  • Update the docs with the code. A page that is wrong is worse than none. The contract test catches a renamed file, not a wrong sentence.
  • Read a school's data only through db.session so the routing keeps its guarantee.
  • Do not add a public page to a school's address. It is a portal, deliberately.
