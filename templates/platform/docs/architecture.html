The one rule

A request belongs to exactly one school, and that is decided by the address it arrived at, and by nothing else. Not a URL parameter, not a form field, not a cookie. Everything else in the architecture exists to make that rule impossible to break by accident.

If a school could be chosen by something a visitor controls, one careless route could show school A's children to school B's staff. So the school is chosen once, at the very start, from the Host header, and after that the database connection itself is that school's: there is nothing left to forget to filter.

The life of a request

  1. The address is read. {{ file('control_plane/resolver.py') }} runs first, before any other hook. It normalises the Host header and asks the registry which school owns it.
    • A platform host (BRIGHTSTARS_PLATFORM_HOSTS): no school is selected. Only /platform, /marketing, /docs, / and shared static files are served; anything else is a designed "not found" page.
    • An unknown host: a designed "address not found" page. No application code runs.
    • A suspended school: a designed "portal paused" page (HTTP 503).
    • A school: it is stored in a ContextVar ({{ file('control_plane/context.py') }}) for this request, and in g.tenant.
  2. Old sign-ins from another school are thrown away. Every session is stamped with its school's id. A cookie from school A shown to school B fails the stamp and is discarded, so a cookie copied between schools authenticates nowhere.
  3. The sign-in is judged. {{ file('core/session_guard.py') }} decides whether the session is still good (see below).
  4. Small hooks run: the admin workspace boundary, live presence tracking ({{ file('app.py') }}).
  5. The route runs. Its decorators check who is asking (@admin_required, @student_required, ...) and, for anything that changes data, the CSRF token (@csrf_protect). Any query it makes goes to this school's database.
  6. The response is finished. Security headers are added; on a school's pages the school's two brand colours are injected as CSS ({{ file('core/theme.py') }}). A heartbeat script is added for signed-in people.
  7. The school is deselected. A teardown hook closes the database session while the school is still current, then clears it.

The order matters and is fixed: the resolver must be installed before any other hook is registered, because every later hook queries the database and needs the school already chosen. {{ file('app.py') }} does this near the top.

There is no default registry URL because a wrong guess would silently create an empty registry, and every school would look as though it had never existed. PostgreSQL is the only database: the tests run against it, and constructs only SQLite understands are forbidden (a contract test enforces it).

How db.session finds the right school

{{ file('control_plane/routing.py') }} replaces Flask-SQLAlchemy's session with a TenantSession. When a query runs, the session asks "which school is current?" and uses that school's engine. Each school has its own connection pool, cached and reused. The rest of the code just writes db.session.execute(...). It fails closed: with no school selected the query raises rather than guessing.

Never use db.engine. It names the default bind, which is the registry, and holds no school data. Use control_plane.routing.current_engine() if you truly need an engine.

A school's files

{{ file('core/storage.py') }} gives each school a folder, tenants/<code>/, with data/ (its question banks as JSON), uploads/ (pictures, signatures, attachments) and numbering.json. Copying that folder plus dumping that database moves the whole school. Uploaded files are served by one route in {{ file('app.py') }} (uploaded_file), and {{ file('core/upload_access.py') }} decides, folder by folder, who may open what: a child's photo is visible to staff, that student, and a parent linked to them; branding pictures are public because the sign-in page needs them.

Sessions and the "launch id"

A session is a signed cookie. Nothing in it expires by itself, so {{ file('core/session_guard.py') }} adds two rules, decided before any route runs:

  1. A restart signs everyone out, except people sitting an exam. Every start writes a fresh random launch id into the registry ({{ file('control_plane/launch.py') }}). Sessions carry the id they were opened under; a mismatch means "from before the restart". If that person has an unfinished exam right now, the session is kept and re-stamped so they carry on; everyone else meets the sign-in page.
  2. Changing a password ends the account's other sign-ins. Each session also carries a fingerprint of the password hash it was opened with. A different hash means the old sessions stop working, however the password was changed.

The launch id lives in the registry, not in process memory, because a deployment may run several workers and they must agree. If the registry or school database cannot be read, nobody is signed out: an outage must never cost a room full of candidates their exam.

Changing data safely

  • CSRF. Every state-changing route is decorated with @csrf_protect ({{ file('core/security.py') }}); every form carries _csrf_token. A contract test lists all write routes and fails if a new one is not exercised against PostgreSQL.
  • Refusals are explained. A number too big for a database column, or text containing a NUL byte, is answered with a plain 400 ({{ file('core/request_errors.py') }}), never a 500. A request over the size limit is answered with the limit and the size sent.
  • Audit. Significant actions call audit_log; the entry records who, what, on which target, from which address.
  • After the commit. Messages to parents are sent only after the change they report was committed, and on a background thread ({{ file('core/background.py') }}) so nobody waits on a mail server and a failed message never undoes what was saved.

Background work

There is no job queue. {{ file('core/background.py') }} runs best-effort work on a thread as the same school: it captures the school and the request's address, then opens a fresh application context and school context inside the thread, so anything that builds a link or reads branding works exactly as in a request. It never raises. Setting BACKGROUND_INLINE in the app config runs the work in the calling thread, which is how the tests make it deterministic.

It is deliberately small. If a job must survive a restart, retry, or be visible to an operator, that is the day to introduce a real queue; see {{ page('recommendations', 'Recommendations') }}.

Errors

{{ file('app.py') }} registers handlers for HTTP errors and unexpected exceptions that render designed pages ({{ tpl('error_4xx.html') }}, {{ tpl('error_5xx.html') }}), per school and in the school's colours, without leaking internals. Requests that arrive where no school can be chosen get the platform's own notice page instead, rendered straight from the template because normal rendering would look the signed-in person up in a school database that does not exist there.

Design decisions worth knowing the reasons for

DecisionReason
A database per schoolIsolation you can reason about; per-school backup and restore; a whole school moves by copying one database and one folder.
No public website for schoolsA school's address is a portal. The company's marketing site is separate; the platform itself serves only /marketing and /docs, on platform hosts.
Restart signs everyone outThe signing secret does not change, so without this a cookie would outlive every restart. The exam exception protects people mid-paper.
Numbering is a pattern, not codeTyped Python that the server runs would let anyone who reached the console run code on a server that can reach every school's database. A pattern is read, never executed.
No existing-school importEvery school is created from scratch through the platform. Do not reintroduce an import-an-old-installation path.
Schema declared once, in models/No migration scripts to drift; a column-diffing helper adds what an older database lacks.
