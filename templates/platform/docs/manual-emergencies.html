Step-by-step plans for the bad days. Read the whole playbook once before acting; the order matters. Each ends with what to check and what to tell the schools.

Before any recovery that writes to a database: take a copy first (python -m control_plane export-tenant CODE for one school, or your database provider's snapshot for everything). A recovery done in a hurry without a copy can turn one problem into two.

Outages

Every school is down

You see
Nothing opens; or every page shows an error; or the proxy shows 502.
Why

One of: the application stopped, the registry database is down, the server is out of memory or disk, or a bad deploy.

Fix
  1. curl -s http://127.0.0.1:8000/health on the server. No answer: the application is down: systemctl status brightstars, then {{ page('manual-startup', "It won't start, or a deploy failed") }}.
  2. It answers but pages fail: the registry or databases. {{ page('manual-database', 'Databases and connections') }}.
  3. df -h and free -h: a full disk or no memory stops everything; clear old logs, add space.
  4. Started right after a deploy: roll back ({{ page('manual-startup', "It won't start, or a deploy failed") }}, Rolling a bad deploy back).
Check
A school's sign-in page opens and someone can sign in.

The server went down during an exam

You see
Entrance candidates or students were in the middle of a timed paper when the server or the power went off.
Why

Answers are saved on the server as they are given. People mid-paper are never signed out by a restart, and their attempt is waiting for them. The exam clock is kept by the server and keeps running while it is down.

Fix
  1. Bring the server back first (above). Do not run new-launch or rotate the secret now.
  2. Tell candidates to reload (or sign in on another computer): they continue with their answers.
  3. Papers whose time ran out are finished from the saved answers.
  4. For candidates who lost real time, grant a retake from their page afterwards ({{ page('manual-entrance', 'Entrance exams and admissions') }}).
Check
Attempts show their saved answers; nobody reports lost work.

One school is down

You see
One school fails; the others work.
Why

Its database, its db_url, its files, or it is suspended.

Fix

{{ page('manual-addresses', 'Addresses, domains and proxies') }} (Portal paused?) and {{ page('manual-database', 'Databases and connections') }} (One school shows the error page).

Check
The school opens.

Data

Restoring one school from its export

You see
A school's data was damaged or lost (a bad import, a mistaken delete, a broken database).
Why

Each school is one database plus its files, so it can be put back on its own without touching any other school.

Fix
  1. Suspend the school so nobody writes to it meanwhile: {{ route('platform_school_status') }} or suspend CODE --reason "restoring".
  2. Export what is there now (export-tenant CODE), so the current state is not lost.
  3. Find the export or backup to restore: an export-tenant folder holds database.sql, the uploads and a README with the exact steps.
  4. Create an empty database and load it: createdb brightstars_CODE_restored, then psql brightstars_CODE_restored < database.sql.
  5. Copy the uploads back (local folder or bucket prefix).
  6. Point the school at the restored database: set-db-url CODE postgresql+psycopg://…/brightstars_CODE_restored, then upgrade CODE.
  7. Check it, then reactivate: activate CODE.
Check
The school's records are as expected. Tell the school what period of changes (between the backup and now) must be re-entered.

A school was deleted by mistake

You see
A school is gone from the console.
Why

Delete exports the school first, then removes its database, files and registry row. Force delete takes no export.

Fix
  1. Find the export folder (the delete printed or showed where it went; on the console it is where exports are written).
  2. Create the school again with the same code (the address and database name follow from it), with no starter banks.
  3. Load the export into its database and files, following the export's own README and Restoring one school above.
  4. Re-add any domains of its own.
Check
Its people sign in with their old passwords and see their records.

Only the super admin, and admins individually granted it, can delete a school, and it is recorded in the activity log ({{ route('platform_activity') }}).

A bulk import put wrong data in

You see
An import created students twice, or in the wrong class.
Why

Every valid row is committed on its own, so a wrong file imports in full.

Fix

For a handful: archive the duplicates (they keep a record; nothing is deleted) and correct classes on each student's page. For hundreds: restore the school from just before the import (above), then import the right file.

Check
Class registers show the right counts.

Security incidents

An account may have been taken over

You see
Someone reports changes they did not make, sign-ins they did not do, or a password they did not change.
Why

A stolen or guessed password, or a sign-in left open on a shared computer.

Fix
  1. Lock the account: staff are suspended by the School Admin (Settings › Staff › ⋯ › suspend); a platform admin is removed by the super admin ({{ route('platform_team') }}). Suspending ends their sign-ins on the next click.
  2. Reset the password (that ends every other sign-in of the account at once).
  3. Read what the account did: the school's activity log ({{ route('admin_audit_logs') }}) and, for platform admins, {{ route('platform_activity') }}. Undo the damage.
  4. If a platform admin's account was taken: also check every school they entered, and consider signing everyone out (new-launch).
Check
No new activity from that account; the person signs in with a new password.

BRIGHTSTARS_SECRET (or the whole .env) leaked

You see
The .env file, or the secret, was exposed (pasted somewhere, committed, a stolen laptop).
Why

With the secret, someone could forge sign-in cookies. With the database URLs, reach the data directly.

Fix
  1. If BRIGHTSTARS_DELIVERY_KEY is not set, set it to the old secret's value first (stored mail, SMS and Paystack secrets are encrypted under a key derived from it), then rotate it properly later ({{ page('manual-messaging', 'Email, SMS, background jobs and alerts') }}).
  2. Set a new BRIGHTSTARS_SECRET on every server and restart: every sign-in in the world ends.
  3. Change every database password in the leaked URLs (registry and schools' roles), and update the URLs.
  4. Rotate the S3 keys, the SMTP and SMS credentials, and the alert webhook if they were in the file.
  5. Ask schools to rotate their Paystack secret keys if the delivery key leaked too.
Check
Old cookies no longer work; services still connect with their new credentials.

Sign everyone out, everywhere, now

You see
You need every sign-in ended immediately (a suspected break-in, a policy change).
Why

A new launch ends every sign-in, except people sitting an exam.

Fix

python -m control_plane new-launch, or the button on {{ route('platform_settings_new_launch') }}. To also end sign-ins of people mid-exam, change BRIGHTSTARS_SECRET and restart (after setting BRIGHTSTARS_DELIVERY_KEY as above).

Check
Any open page goes to the sign-in page with "The system was restarted".
