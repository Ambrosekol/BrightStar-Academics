The rules of the house, each with the reason behind it. Most are enforced by a contract test, so breaking one fails the build rather than a school.

The rules

Register routes with plain @app.route

Every blueprints/*/routes.py does from app import app and decorates that shared instance, rather than creating Blueprint objects. This keeps every endpoint name (and therefore every url_for(...) and every entry in the permission map) stable and prefix-free, at the cost of Blueprint features like URL prefixes. New route modules are imported at the bottom of {{ file('app.py') }} for their side effect.

Never use db.engine

It names the default bind, which is the registry and holds no school data. Use db.session for school data (the routing gives it the current school), or control_plane.routing.current_engine() when you need an engine.

PostgreSQL only: nothing SQLite-shaped

Upserts go through core.db_helpers.insert_stmt() and string aggregation through group_concat() ({{ file('core/db_helpers.py') }}); partial indexes declare postgresql_where. A contract test enforces it. Corollaries you will meet:

  • An expression that is selected and grouped must be one expression object. func.coalesce(col, 'x') written twice becomes two different bind parameters and PostgreSQL rejects the grouping. Build it once and reuse the variable in both places.
  • An integer column has a fixed size: never assume Python's unlimited integers reach the database. The application already answers oversize numbers with a plain 400; still validate what you read from a form.
  • Text with a NUL byte is refused by PostgreSQL; the same 400 covers it.

Never hard-code a school

Use school_brand in templates and core.branding.school_name() in code. There is no default school and no school-specific string anywhere; the tests search for any that appears.

The schema lives in models/, and only there

No CREATE TABLE script, no migration files. create_all() makes tables; a column-diffing helper adds missing columns to existing databases. So: a new column needs a default (or nullable), and a rename is a new column plus a copy, never an ALTER hidden in code. Conventions ({{ file('models/__init__.py') }}): timestamps are ISO-8601 UTC text, flags are integer 0/1, marks are floats.

Do not import an old installation, and do not ship a school's data

Every school is created from scratch through the platform. The import-an-old-installation commands and the SQLite import code were removed on purpose; do not reintroduce them. No school's own questions ship with the platform: a new school starts from starter_banks/ or imports its own.

Never run anything typed on a web page

No eval, exec, dynamic import or template engine on user-provided text. Numbering is a pattern that is read, never executed. If a new feature seems to need code as data, design a small checked language instead.

Use the design system

School pages use the tokens in static/school-ui.css; do not add colours or sizes. Fonts are self-hosted. The platform console, docs and marketing page have their own stylesheets. Uploads: always show the real limit beside a file box and explain any refusal ({{ file('core/uploads.py') }}, static/upload-limit.js).

Notify after the commit, never inside it

Messages to parents are best-effort and must never roll back or block what triggered them. Call the sender only after your own db.session.commit() succeeded, and for anything slow register it with @job_handler('name') and call it through enqueue('name', **kwargs) ({{ file('core/jobs.py') }}), never a bare thread: a job's arguments must be JSON-serialisable (ids, not ORM objects), and it opens its own database session, so it cannot see uncommitted changes.

Audit significant actions

Call audit_log(action, module, target_type, target_id, details) for anything an administrator would want to be able to find later, and add a human sentence for the action to the friendly dictionary in {{ file('core/security.py') }}. Never put a secret in details.

Every write route gets a real submission

A route that accepts a POST but is neither submitted in tests/verification/write_paths_pg_posts.py nor listed with a reason in pg_posts_coverage.py fails the contract suite. Add the submission and list the route pattern. See {{ page('testing', 'Testing') }}.

Style

  • Match the file you are in. Some older route files are dense (several statements to a line, terse names). Keep that style when fixing them; do not reformat a whole file to make a two-line change. New modules should be clearer: short functions, a module docstring explaining why, comments only for non-obvious reasons.
  • Every module has a docstring that says what it is for and any rule a reader must know. The Reference pages are built from them.
  • Explain refusals in plain words. A form that fails says what to change ("Enter the payment amount as a number of naira, for example 12500.50"), not "invalid input".
  • Line endings. Many files use Windows (CRLF) line endings. Let your editor preserve them; a tool that rewrites a file with different endings turns a small change into a whole-file diff.
  • Templates escape by default. Never use |safe on anything that came from a person.

Announcing a change to users

Put a note in {{ file('release_notes.json') }} at the project root; it is the only place a release note is written, and the file has comments that explain its rules. Each release has a version that must go up, and each change names an audience: staff, family or student. Staff changes may name one staff guide page in help; family and student changes must not, and the contract test {{ file('tests/current/test_release_notes_contract.py') }} fails if one does. Do not reword a release people may already have seen; add a new one instead.

Mistakes worth not repeating

MistakeWhat happensDo this instead
Reading a school id from the URL or a form to choose a schoolOne careless route shows a school's data to another.Never. The address alone chooses the school.
Adding an admin route without a permission map entryIt is guarded only by admin.access.Add it to ADMIN_ENDPOINT_PERMISSIONS.
Grading from the live question bankAn edited question changes a past result.Grade from the frozen attempt questions.
Writing a practice run to the databaseIt could count towards grades.Practice is stateless: nothing is stored.
Sending a message before the commitA message about something that then rolled back.Send after the commit, on the background helper.
Testing only the page, not the submitA query PostgreSQL rejects ships.The POST script exists for exactly this.
A test that shares one database between "schools"Isolation tests pass for the wrong reason.Each test school needs its own database (the helper builds the names from a {slug} template).
