Two halves: the platform and the schools

The single most useful thing to know is that the code has two separate worlds.

The platform (control_plane/)A school (models/, blueprints/, core/)
Who uses itBrightstars operatorsA school's staff, students, parents, candidates
Where the data isThe registry database, one for the whole deploymentThat school's own database. One per school.

Sign-in{{ file('control_plane/entry.py') }}{{ file('blueprints/auth/routes.py') }}

Never mix them. A school's route must never read the registry directly, and the platform must never query a school's tables except through the deliberate, read-only paths in {{ file('control_plane/provisioning.py') }} and {{ file('control_plane/team.py') }}.

How one feature is spread across the code

Take "a parent sees their child's report card". It touches, in this order:

a URL and a guard
{{ file('blueprints/parents/report_cards.py') }}→ the rules and the numbers
{{ file('blueprints/school/report_card_data.py') }}→ the tables
{{ file('models/school.py') }}→ the drawing
{{ file('core/report_card_pdf.py') }}→ the page
{{ tpl('report_card_page.html') }}

The pattern repeats everywhere: a route module (thin: check who, read the form, call, redirect or render), a helper or data module (the rules), models, sometimes a drawing module, and a template. When a route file is large, look for its neighbouring helpers.py; the real logic is usually there.

The shared helpers

{{ file('core/security.py') }} is the one to learn first: the permission catalogue, role presets, the endpoint-to-permission map, admin_required, csrf_protect, audit_log. Next {{ file('core/db_helpers.py') }} (query helpers and the dialect-neutral upsert), {{ file('core/branding.py') }} (a school's name, colours, logo: never hard-code them), {{ file('core/storage.py') }} (a school's folders), {{ file('core/uploads.py') }} (every image upload) and {{ file('core/delivery.py') }} (a school's own email and WhatsApp).

Habits of this codebase that surprise newcomers

  • Plain @app.route, no Blueprint objects, so endpoint names stay stable. Every url_for and every entry in the permission map depends on that.
  • Rows behave like dictionaries (row['name']) as well as objects. Older templates rely on it.
  • Dense, compact Python in some older route files (several statements on a line). Match the surrounding style when you edit; do not reformat a file you are only fixing.
  • Everything about "which school" is implicit. You will not see a school_id in most queries: the database itself is the school. That is deliberate.
  • Timestamps are text in ISO-8601 UTC, and yes/no flags are integers 0 or 1.
