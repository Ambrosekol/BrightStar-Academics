For whoever has to go from "this is broken" to the line of code that does it. You do not need to know the whole codebase: every page has one route, every route lives in one file, and the reference pages say which. The tour of the code ({{ page('tour', 'A tour of the code') }}) and the contributing notes ({{ page('contributing', 'Contributing') }}) go deeper.

How one request travels

Address
resolver.py: which school→ Sign-in
session_guard.py: still good?→ Workspace
app.py: School or Entrance→ Permission
security.py: admin_required→ The route
blueprints/…→ The page
templates/…
  1. {{ file('control_plane/resolver.py') }} reads the address and selects the school (or answers Address not found / Portal paused). From here on every database query goes to that school's own database.
  2. {{ file('core/session_guard.py') }} decides whether the sign-in is still good (restart, password change, idle, lifetime, signed out).
  3. enforce_admin_workspace_boundary in {{ file('app.py') }} keeps School and Entrance pages apart.
  4. admin_required in {{ file('core/security.py') }} checks the page's permission from ADMIN_ENDPOINT_PERMISSIONS; the route then checks finer things itself (this class? this student?).
  5. The route (a function under blueprints/) does the work and renders a template under templates/.
  6. After it, {{ file('app.py') }} adds the security headers and the school's colours.

Finding the code behind a page

From an address to its file

You see
A page at, say, /admin/finance/new-students misbehaves.
Why

Every address has exactly one route function.

Fix
  1. Search these docs for the address (the box at the top) or open {{ page('reference-routes', 'Routes') }}: it names the function, its file and the permission it needs.
  2. Or in the code: grep -rn "new-students" blueprints/ app.py.
  3. The function's render_template('…') names the page's template.
Check
You can point at the function and the template.

From a piece of data to its table

You see
A number or a record is wrong, and you want to look at it in the database.
Why

Every table of a school and of the registry is described, column by column.

Fix

Open {{ page('reference-data', 'Data model') }}, or search for the column name. Models live in models/ (a school) and {{ file('control_plane/models.py') }} (the registry).

Check
A SELECT on that table in the school's database shows the record.

Debugging

A page shows the 500 error page

You see
"Something Went Wrong" (500 Server Error) for a page.
Why

An unexpected error. The page never shows details (they could leak data), but the full traceback is written to the log.

Fix
  1. Read the log at that moment: journalctl -u brightstars --since "10 min ago" (or wherever gunicorn's output goes).
  2. The last lines of the traceback name the file and line; the line just above Error: names the cause.
  3. A database error (UndefinedColumn, IntegrityError) usually means an upgrade is missing or bad data; anything else is a code bug: reproduce it locally (next entry).
Check
You can say which line failed and why.

Reproducing a problem safely on your own machine

You see
You need to see the bug happen without touching real schools.
Why

Never debug against production data: schools hold children's records.

Fix
  1. Run the platform locally ({{ page('getting-started', 'Getting started') }}) and create a test school.
  2. Recreate just enough data by hand to show the bug.
  3. Better still, write it as a test: the end-to-end scripts in tests/verification/ create throwaway databases, drive the real application and delete everything afterwards. Copy the closest one and add a check that fails because of the bug.
  4. If a real school's data is truly needed, export it (export-tenant) to an encrypted machine only with the school's permission, and delete it afterwards.
Check
The failing test fails before your fix and passes after.

A button spins for ever, or does nothing

You see
Pressing a button shows a spinner that never ends, and nothing is saved.
Why

Pages load in place through {{ file('static/inplace.js') }}. A script error stops the form being sent. One real case: a form with a field named method hid the form's own method property and broke sending (scripts must use form.getAttribute('method'); a contract test guards this).

Fix
  1. Open the browser's developer tools (F12) › Console, press the button, and read the red error.
  2. Network tab: was a request sent? What did it answer?
  3. Fix the script or the template the error names.
Check
The form saves and the next page opens.

Shipping a fix

From a fix to production

You see
The fix works locally.
Why

A safe path from your machine to the schools.

Fix
  1. Run the contract suite, and the end-to-end scripts for the area you changed (the Testing page lists them by area; {{ page('testing', 'Testing') }}). Before a release also write_paths_pg_smoke.py and write_paths_pg_posts.py.
  2. On Windows, make sure files keep Unix (LF) line endings.
  3. Add a release note in release_notes.json if anyone will notice the change.
  4. Commit, push, and deploy in the safe order ({{ page('manual-startup', "It won't start, or a deploy failed") }}).
Check
The reported problem is gone in production, and the What's new card shows the note.
