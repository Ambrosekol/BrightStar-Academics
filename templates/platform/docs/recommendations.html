Advice from the people who built it, ordered roughly by how much each item protects you. None of it is a known fault: the codebase's "Known gaps" list is empty. These are things we would do next, and things to watch as the platform grows.

Before the first paying school

  1. Run the whole verification suite against staging with production-like settings ({{ page('testing', 'Testing') }}). Especially the multi-school isolation script.
  2. Set up backups and test a restore of one school into a scratch server. A backup you have never restored is a hope.
  3. Add two-factor authentication for platform admins. A platform admin can enter any school. Their sign-in is the most valuable credential in the company.
  4. Decide the email and SMS story. Either give every school its own sender (recommended: parents recognise the school) or run a shared platform sender. For SMS, apply for approved message templates so notices can reach parents outside the 24-hour window; today the application sends free-form messages only.
  5. Have a teacher of each subject review the standard question banks before a school relies on them for real admissions decisions.

Hardening

Five items that used to sit here as advice are done; this is now what each of them actually is.

  • A separate database role per school is a command away, not a manual DBA task. python -m control_plane create-db-role CODE [--rotate] creates a role that owns exactly one school's database and nothing else and prints its connection string; set-db-url CODE URL is the separate, deliberate step that actually points the registry at it (a literal URL, or the already-supported env:VARIABLE_NAME indirection, so a live password need not sit in the registry's own database). {{ file('control_plane/provisioning.py') }}. Both are also on the Settings page's Terminal actions, for a highly-trusted admin.
  • script-src no longer allows 'unsafe-inline'. Every onclick/onchange/onsubmit attribute in every template - about a hundred of them - was moved to {{ file('static/interactions.js') }} (a handful of delegated, data-*-attribute-driven listeners); every inline <script> left carries a fresh per-request nonce (csp_nonce(), app.py). style-src keeps 'unsafe-inline' deliberately: a school's own colours are already restricted to #rrggbb before they reach a <style> block, where a nonce buys nothing.
  • A dedicated poller for background jobs. {{ file('core/jobs.py') }}'s own retry is opportunistic (a stuck job waits for something of the same kind to be enqueued again); jobs.sweep_all_kinds() gives every stuck job, of any kind, another try, and python -m control_plane sweep-jobs [CODE] runs it across every school - meant for a cron/systemd timer, with no new service to deploy.
  • Alerting ({{ file('core/alerting.py') }}) on the four log lines that signal degraded safety: the registry being unreachable ({{ file('control_plane/launch.py') }}), a job that has used up its retries ({{ file('core/jobs.py') }}), a burst of delivery failures for one school (not a single honest bounce), and a sign-in rate limit actually being hit. Set BRIGHTSTARS_ALERT_WEBHOOK to have each one also post to it (Slack's own incoming-webhook format works as-is); with nothing set, they only log, exactly as before.
  • Rotating the platform secrets on a calendar was already safe for the session secret (a sign-out is the only cost) but not for BRIGHTSTARS_DELIVERY_KEY: every school's mail password, SMS API token and Paystack secret key are encrypted under it, so changing it outright would have silently broken every one of them at once. {{ file('core/secrets_rotation.py') }} decrypts a school's own secrets under the old key and re-encrypts them under the new one first; python -m control_plane rotate-delivery-key OLD NEW [CODE] runs it across every school (or one), so the environment variable itself is only ever changed once every school shows nothing unreadable. The Settings page's rotation wizard (a highly-trusted admin only) is the same operation from the portal: it runs the move, will not offer to set the variable until every school shows 0 skipped, and re-checks that itself at the moment the variable is actually set, rather than trusting an earlier click. {{ file('control_plane/settings_console.py') }}.

Product recommendations

  • Offer parents a "notify me" choice (channels and quiet hours). Today every parent with a contact on file gets every notice.
  • A notice log per school. Done: every guardian email/SMS attempt (a new assignment, a fee charged, a released report card or exam timetable) is recorded to {{ table('notification_delivery_logs') }} and viewable at {{ route('admin_notification_log') }}, linked from the Activity Log and from a student's own page. Receipts already had their own, older version of this ({{ table('finance_delivery_logs') }}).
  • Bulk release with a preview, for a whole class. Done: {{ route('admin_school_results_release_class') }} shows every student in the class with an approved-but-unreleased result for the chosen session and term - how many subjects, how many already released, how many still waiting - before anything changes, then releases only the students who actually have something approved in one step, exactly complementing the existing one-student-at-a-time button.
  • Data export for a school leaving. Done: python -m control_plane export-tenant CODE [--output DIR] ({{ file('control_plane/provisioning.py') }}'s export_tenant_data) writes a plain-SQL pg_dump of the school's own database, a copy of its own uploads folder, and a README explaining how to bring both back elsewhere - one new directory, nothing else to assemble by hand.
  • Let a question bank's questions be reordered from the screen. Done: {{ tpl('admin_bank.html') }} now has an up/down button on every question, each carrying the whole new order (computed once, server-side, in the template - no client-side arithmetic to get wrong) to the route that already existed ({{ route('admin_reorder') }}, permission {{ perm('questions.reorder') }}); a small admin.js function posts it and reloads on success, so no page navigation is needed for what used to be a fixed order at creation.
  • A refund for an online payment. Done: a Paystack-made payment's own receipt page now has a Refund via Paystack button (the same permission as voiding a payment, {{ perm('finance.manage') }}), which calls Paystack's own POST /refund ({{ file('core/payments.py') }}) and records it in {{ table('finance_refunds') }} as 'pending' - starting a refund is not the same as it having actually happened. Only Paystack's own refund.processed/refund.failed webhook (now read at {{ route('paystack_webhook') }}) settles it: 'processed' is the one moment the original payment is voided, with a void reason that says so; 'failed' leaves it exactly as it was, since no money moved. A school whose webhook was never set up is not stuck either - reconcile_pending_refunds() asks Paystack directly for a refund still 'pending' after two minutes, opportunistically, the same self-heal {{ route('admin_finance_dashboard') }} already gave a stuck payment.

How to keep the codebase healthy

  • Every write route gets a real submission in the PostgreSQL script ({{ page('testing', 'Testing') }}). The guard enforces it; do not work around it by listing a route as exempt without a reason.
  • A real admin route needs a real link, not just a permission. Nothing enforces this one automatically: a route can be fully built, correctly permissioned and exercised by the PostgreSQL script, and still be unreachable by an actual person because nothing in the UI ever points to it - the promotion feature, two of the three result exports, a bank's JSON export, and the candidate/project delete buttons were all found in exactly this state in one pass. When adding a page or action, follow it back to where a person would actually click to reach it, the same way the nav-coverage contract already does for the navigation rail itself ({{ file('tests/current/test_guide_covers_every_nav_page.py') }}).
  • Update the docs with the code. A page that is wrong is worse than none. The contract test catches a renamed file, not a wrong sentence.
  • Read a school's data only through db.session so the routing keeps its guarantee.
  • Do not add a public page to a school's address. It is a portal, deliberately.
