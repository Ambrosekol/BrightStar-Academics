There are two kinds of database, and it matters which one a problem is in:

  • The registry (BRIGHTSTARS_PLATFORM_DB): which schools exist and their addresses, the platform team, the shared sign-in limits, ended sign-ins and the launch id. If it is down, nothing can be routed and the console does not open.
  • One database per school (named brightstars_<code> by default, or wherever its db_url points): everything inside that school. If one is down, only that school is affected.

Handy commands, run on the database server with psql:

SELECT datname, state, count(*) FROM pg_stat_activity GROUP BY 1, 2 ORDER BY 3 DESC;   -- who holds connections
SHOW max_connections;                                                                     -- the ceiling
SELECT pid, now() - query_start AS running, left(query, 120) FROM pg_stat_activity
 WHERE state = 'active' ORDER BY 2 DESC LIMIT 10;                                         -- the slowest queries right now

A database cannot be reached

Every school shows the error page; the console does not open

You see
The 500 page everywhere; the log shows OperationalError / "connection refused" / "could not connect to server" for the registry.
Why

The registry database is down or unreachable. With no registry the application cannot tell which school an address belongs to. (The sign-in limits fall back to each worker's own count, and nobody is signed out because of it.)

Fix
  1. Is PostgreSQL running? sudo systemctl status postgresql (or your provider's status page).
  2. Can the app server reach it? psql "<BRIGHTSTARS_PLATFORM_DB without +psycopg>" -c "select 1".
  3. Out of disk on the database server is a common cause: df -h.
  4. If BRIGHTSTARS_ALERT_WEBHOOK is set, a registry_unreachable alert was posted when it started.
Check
python -m control_plane list answers; schools open.

One school shows the error page; the others are fine

You see
Only one school's pages fail; the log names its database.
Why

That school's own database is down, renamed, dropped, its role's password changed, or its db_url in the registry is wrong.

Fix
  1. python -m control_plane list shows the database each school uses.
  2. If it uses env:VARIABLE_NAME, that variable must be set on every server (the error says "Environment variable … is not set; it holds a school database URL").
  3. If you gave it its own role ({{ route('platform_settings_create_db_role') }}) and the password was rotated, update the URL with set-db-url or {{ route('platform_settings_set_db_url') }}.
  4. If the database really is gone, restore it from its export or backup (see {{ page('manual-emergencies', 'Emergency playbooks') }}).
Check
The school's sign-in page and Overview open.

Out of connections

"too many clients already" / "remaining connection slots are reserved"

You see
Random pages fail with FATAL: sorry, too many clients already or remaining connection slots are reserved, while the database is not busy.
Why

Each school gets its own small connection pool in every running worker, and the registry has one more ({{ file('control_plane/routing.py') }}). The total is roughly schools in use × (pool + overflow) × workers + the registry's pool × workers. With many schools or workers it exceeds PostgreSQL's max_connections (often only 20–100 on a small managed plan).

Fix
  1. Right now: restart the application (closes its connections), or close idle ones: SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'idle' AND datname LIKE 'brightstars_%'; (this only rolls back unfinished work; nothing saved is lost).
  2. Lasting: lower the pools: BRIGHTSTARS_DB_POOL_SIZE=1, BRIGHTSTARS_DB_MAX_OVERFLOW=1, and BRIGHTSTARS_REGISTRY_POOL_SIZE/_MAX_OVERFLOW to fit; fewer gunicorn workers with more threads.
  3. Lasting, at scale: put PgBouncer in transaction mode in front of PostgreSQL (Aiven and most providers offer one). Use a database per school (the default), not a schema per school, with PgBouncer.
  4. BRIGHTSTARS_SCHOOL_ENGINE_IDLE_SECONDS (600) closes a quiet school's connections after that long; lower it if many schools are rarely used.
Check
The first query above shows connections well under max_connections at a busy time.

Schema and upgrades

"column … does not exist" / "relation … does not exist"

You see
UndefinedColumn or UndefinedTable in the log after a deploy.
Why

That database was not upgraded since the code changed. Tables and columns are declared in the models and added by create_all() plus a column-adding step; there are no migration scripts.

Fix

python -m control_plane upgrade (every school and the registry) or upgrade CODE, or {{ route('platform_settings_upgrade') }}.

Check
The page opens.

The contract test reports "model/schema drift"

You see
FAIL test_models_match_db.py: model/schema drift: … modelled but not in DB: […]
Why

The test compares the models with a real school database on the machine running it. On a developer machine it fails right after a change that adds a column, until that machine's databases are upgraded.

Fix

Start the app once, or run python -m control_plane upgrade, then run the tests again. On a server it means the deploy skipped the upgrade step.

Check
The contract suite passes in full.

"retired tables" still hold rows

You see
A warning during upgrade that a retired table (school_public_pages, school_public_news, school_public_enquiries) still holds rows.
Why

Those belonged to the removed website editor. Upgrades drop them only when empty, so nothing is lost by accident.

Fix

python -m control_plane drop-retired-tables shows what each school still holds; read it, and if nothing is needed, add --yes to drop them for good.

Check
The next upgrade gives no warning.

Slow pages

Every page is slow

You see
Pages take seconds everywhere, for every school.
Why

Each page asks the database a handful of small questions; if the database is far away (another region) or overloaded, every one of them waits. Menu counts and permissions are already kept for a few seconds per worker ({{ file('core/short_cache.py') }}), so an ordinary staff page reads only its own content.

Fix
  1. Put the application and the database in the same region (a round trip across continents adds 100–300 ms per query).
  2. Check the slowest queries (the third query at the top of this page) and the database's CPU.
  3. Check the server is not swapping: free -h; give gunicorn fewer workers if memory is short.
  4. Raise the cache lifetimes a little on a very busy deployment (BRIGHTSTARS_ADMIN_CACHE_SECONDS, BRIGHTSTARS_BADGE_CACHE_SECONDS, BRIGHTSTARS_REGISTRY_CACHE_SECONDS), knowing changes then take that long to show on other workers.
Check
A staff Overview loads in well under a second.

One page is slow

You see
One page (a big class list, a whole-class PDF, a large import) is slow; others are fine.
Why

Some pages genuinely do a lot: a class's report-card PDF draws every card; an import checks every row.

Fix

Expected for those. If an ordinary page is slow, note its address and what it shows, and look in {{ page('manual-code', 'Finding and fixing it in the code') }} for how to find the query (the route reference on {{ page('reference-routes', 'Routes') }} names the file behind every address).

Check
The page loads in a reasonable time for its size.

Database roles

Giving a school its own database role

You see
You want one school's data reachable only with its own credentials.
Why

By default one PostgreSQL role connects to every school's database. A role per school limits what a single leaked password can reach.

Fix
  1. python -m control_plane create-db-role CODE (or {{ route('platform_settings_create_db_role') }}). It prints a new connection URL and changes nothing yet.
  2. Store the URL as an environment variable on every server, e.g. SCHOOL_ABC_DB=postgresql+psycopg://….
  3. python -m control_plane set-db-url CODE env:SCHOOL_ABC_DB (or {{ route('platform_settings_set_db_url') }}).
Check
The school opens; list shows its new URL reference.
