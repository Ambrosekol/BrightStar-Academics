The console is where Brightstars operators run the platform: create and suspend schools, manage their addresses and look, and (for the super admin) manage the team. It is served only on the platform hostnames (BRIGHTSTARS_PLATFORM_HOSTS) and is invisible from a school's own address: the guard {{ file('control_plane/console.py') }} calls platform_host_only returns 404 anywhere else, so an outsider cannot even tell the routes exist.

The team: super admin and platform admins

There are two kinds of platform admin, and both have full control over every school: create, brand, suspend and enter any of them.

Create, brand, suspend and enter schoolsyesyes
Add, remove, restore and reset other adminsnoyes

Can be removedby the super adminnever

The first admin created becomes the super admin. The console can never create another (do it deliberately from the command line with --super). A registry that had admins before roles existed promotes its earliest admin automatically on start ({{ file('control_plane/registry.py') }}, ensure_superadmin).

  • Adding an admin ({{ route('platform_team_new') }}) generates a one-time password, shown once. The new admin must replace it at first sign-in, and nothing else opens until they have.
  • Removing an admin ({{ route('platform_team_remove') }}) never deletes the account. It switches their access off everywhere at once: their console session ends, their unused entry tickets die, and their reserved account inside every school is switched off, so a session already open inside a school stops at the next click. The account and its log stay; {{ route('platform_team_restore') }} brings them back with a new temporary password. If a school cannot be reached while removing someone, the console names it, so it is never silently missed.
  • Resetting a password ({{ route('platform_team_reset') }}) gives a new temporary password.
  • Documentation access ({{ route('platform_team_docs_access') }}). On the Team page each non-super admin has a grant / withdraw button. It changes a single flag, platform_admins.docs_access ({{ table('platform_admins') }}), and is written to the activity log. There is no bulk grant and no self-service: only the super admin decides who reads these pages.

Creating and running a school

The Create a school form ({{ route('platform_school_new') }}) is the normal path, because it captures everything the school will look like before the school exists, so nobody ever sees a portal wearing another school's name:

  • Name and code. The code is permanent: it forms the portal address and names the school's database and folder. It can never be reused or renamed.
  • Branding. Name, motto, tagline, phone, email, address and a logo.
  • Sign-in photographs. Up to eight, shown as a slideshow beside the sign-in form.
  • Brand colours. A main and an accent colour with a live preview. Both sit behind white text, so a colour too light to read it is refused (WCAG AA contrast, 4.5:1); the form warns as you pick and the server enforces it.
  • Question banks. Ticked by default: start with the platform's standard entrance banks, copied into the school's own folder.
  • Numbering. How candidate codes and student numbers are written: a pattern with the default already filled in. See {{ page('branding-numbering', 'Identity and numbering') }}.
  • Its own domain (optional) and a first administrator (optional; a one-time password is shown once).

What happens when you press the button is in create_tenant ({{ file('control_plane/provisioning.py') }}). Every choice that can be checked without a school is checked first, so a bad one is reported before a database and a folder exist. Then, in order:

  1. a row in tenants and its portal hostname in tenant_domains, plus the audit entry;
  2. the school's database is created and its schema built (upgrade_tenant);
  3. branding is applied and the numbering rules written to tenants/<code>/numbering.json;
  4. the starter banks are copied in, and the first administrator created if asked.

If any step after the first fails, the half-made school is removed again. The school is reachable the moment it exists at <code>.<portal domain>.

Addresses

Every school gets a portal address the platform owns. It works at once and can never be removed. A school may add its own domain as well: the school creates one DNS record, portal.theschool.example. CNAME theschool.<portal domain>., and the console (or add-domain) registers the hostname ({{ route('platform_school_domains') }}). Your reverse proxy needs a certificate for every hostname it serves (a wildcard for the portal domain, plus one per school domain) and must pass the original Host header through unchanged, because that is what selects the school.

Suspending

{{ route('platform_school_status') }} takes a school offline for everyone (staff, parents, students, candidates) within BRIGHTSTARS_REGISTRY_CACHE_SECONDS on each worker, because host lookups are cached. Data is untouched and returns on reactivation. A reason is recorded.

Look of the portal

Colours, logo and photographs can be changed afterwards from the school's page ({{ route('platform_school_branding') }}) and, if the school's branding.manage permission is granted, by the school's own administrators. Both use the same rules in {{ file('core/branding.py') }} and {{ file('core/theme.py') }}, so they cannot disagree about what is allowed.

Entering a school

Each school is on its own domain, so the console cannot set a session cookie for it. {{ route('platform_school_enter') }} instead mints a token, stores only its SHA-256 (a copy of the registry does not let anyone in), and redirects the operator to the school's own address where {{ route('platform_entry') }} redeems it exactly once, within a short time.

Redemption signs the operator in to a reserved account in that school, platform@<username>, with the school's top-level role. The @ is what keeps this namespace unreachable from anything a person can type when creating a school account. The entry is recorded in the platform audit log and in the school's own audit trail; everything the operator does there is recorded under that account. The banner inside a school shows that a platform operator is present.

Platform admins must be able to do everything a school admin can do, in any school, but they must never share a school's passwords, and their footprint inside a school must be readable by the super admin. A reserved, revocable account per operator achieves all three.

The activity log

{{ route('platform_activity') }} is arranged as choose an admin, then read their log. The super admin can pick anyone (or Everyone, or a removed admin) and filter by Schools, Accounts & team, Sign-ins or Inside schools. It records what each admin did to schools, within the platform (adding, removing, restoring, resetting, docs access, password changes) and every sign-in, sign-out and failed or refused attempt on a real account with the address it came from. "Inside schools" is read, read-only, from each school's own audit trail; only schools the admin has entered are opened, and a school that cannot be reached is named on the page rather than silently omitted. Any other admin sees only their own log. Logic: {{ file('control_plane/team.py') }}.

The command line

Everything above that a console does has a command, for servers and for scripting: python -m control_plane init | create-platform-admin | create-tenant | list | upgrade | new-launch | add-domain | remove-domain | suspend | activate | drop-retired-tables. Full syntax is in the configuration and commands reference.

Sign-in limits

Sign-in (schools and console), password recovery and the email/WhatsApp test buttons are limited per address and username, for example 8 sign-ins per 5 minutes. The counts live in the registry ({{ table('rate_limits') }}), so several workers, or a restart, cannot multiply or reset them. Details in {{ file('control_plane/ratelimit.py') }} and {{ page('security', 'Security model') }}.
