Parents and students are told things by email, SMS and in-app alerts: a receipt, a report card released, a new fee, a timetable released, a password-reset link. Three pieces are involved, and a problem is always in one of them:

  1. The account it is sent from. A school's own mail server and BulkSMS Nigeria account (Settings › Email & SMS, {{ route('admin_school_delivery') }}), or the platform's shared account (BRIGHTSTARS_SMTP_*, BRIGHTSTARS_SMS_*) as a fallback. Rules in {{ file('core/delivery.py') }}.
  2. The background job that sends it ({{ file('core/jobs.py') }}, table {{ table('background_jobs') }}). Nobody waits for a mail server: the work is written down first, then sent, and retried if it fails.
  3. The address it goes to: the guardian email and phone on the student's record, or the parent account's.

Every message tried is recorded: the school's Notice log (Settings › Activity & notice logs, {{ route('admin_audit_notices') }}) shows each one, whether it went, and why not. Start there.

Email

"Email is not set up yet. Save your mail server settings first."

You see
Email is not set up yet. Save your mail server settings first.
Why

The school has no mail server of its own saved, and the platform has no shared one (BRIGHTSTARS_SMTP_HOST empty).

Fix

Either the School Admin enters the school's mail server (host, port, user, password, sender), or you set the platform's shared account in the console ({{ route('platform_settings') }}): BRIGHTSTARS_SMTP_HOST, _PORT, _USER, _PASSWORD, _FROM, and _STARTTLS or _SSL.

Check
Send a test on the Email & SMS page delivers.

A school that has started entering its own mail server never falls back to the platform's, even if its own is incomplete: its parents' mail is never quietly sent from the platform's address.

"The test message could not be sent: …"

You see
The test message could not be sent: the mail server did not accept the username or password. (or: the server could not be reached / the server did not answer in time / a secure connection could not be made / the mail server refused the message)
Why

The reason is said in plain words ({{ file('core/failures.py') }}); the full technical error is in the server log.

Fix
  • username or password: re-enter the password. Gmail and Outlook need an app password, not the account password.
  • could not be reached / refused the connection: check host and port. Only ports 25, 465, 587 and 2525 are allowed; most providers use 587 with STARTTLS. Many cloud servers block port 25.
  • did not answer in time: a firewall drops the traffic; try 587 or 2525.
  • a secure connection could not be made: the security choice does not match the port (465 = SSL; 587 = STARTTLS) or the server's certificate is not valid for its name.
  • refused the message: the sender address is not one the account may send from.
Check
The test email arrives.

"That mail server address is not allowed: it is not a public internet address."

You see
That mail server address is not allowed: it is not a public internet address.
Why

In production a school's mail host must resolve only to public addresses, so nobody can aim the server at your own private network. A local mail catcher works only in development.

Fix

Use the provider's public mail host name. If you run an internal relay for all schools, set it as the platform's shared account instead (the platform's own setting is trusted).

Check
The settings save and the test sends.

Emails go to spam, or arrive with a strange sender

You see
Parents find receipts in spam, or see "via" another domain.
Why

The sending domain does not prove the mail is allowed to come from that server (SPF, DKIM, DMARC records).

Fix

The domain's owner adds the SPF and DKIM records their mail provider gives them, and a DMARC record. Send from an address on that domain.

Check
A test email's headers show spf=pass and dkim=pass.

SMS

"SMS is not set up yet" / "SMS is not connected to your school's own account yet"

You see
SMS is not set up yet. Save your SMS settings first. — or — SMS is not connected to your school's own account yet. — or — The platform provides SMS for every school, so there is no balance for the school to check.
Why

BRIGHTSTARS_SMS_PAYER decides who pays: school (each school connects its own BulkSMS Nigeria account), platform (the platform's one account texts for every school; schools enter nothing), or either (a school's own when it has one, else the platform's).

Fix

With school: the School Admin saves the API token and sender name on Email & SMS. With platform: set BRIGHTSTARS_SMS_API_TOKEN and BRIGHTSTARS_SMS_SENDER_ID in the console.

Check
Check balance shows the wallet; a test text arrives.

"The API token was not accepted." / "… wallet has no balance." / "The sender name is not registered or approved."

You see
One of those three, from BulkSMS Nigeria.
Why

The provider refused: a wrong token (401), an empty wallet (402), or a sender name the provider has not approved (403).

Fix

Copy the token again from the BulkSMS Nigeria dashboard; top up the wallet; get the sender name approved there (it can take a working day), or use one that is.

Check
A test text arrives.

An event did not send a text

You see
A parent got an email but no SMS for something.
Why

SMS costs credit, so only four moments send one: a report card released, a new fee, a payment recorded, and the first message of a conversation the school starts. Everything else is email and in-app only. A guardian phone that is missing or invalid also skips the text.

Fix

Check the notice log for that student: it shows each attempt and its reason. Correct the guardian phone on the student's record.

Check
The next event sends a text.

Background jobs

Messages are late, or never go

You see
Receipts or notices arrive late or not at all; the notice log shows them waiting or failed.
Why

Each message is a row in {{ table('background_jobs') }} (pending → running → done). A try that fails puts it back to pending, to be tried again after two minutes; after the fifth failed try it stays failed. One stuck "running" for five minutes (its thread died in a restart) is tried again. Retries happen when the school next sends something of the same kind, so a quiet school can sit with stuck jobs.

Fix
  1. python -m control_plane sweep-jobs (all schools) or sweep-jobs CODE, or {{ route('platform_settings_sweep_jobs') }}: retries every stuck job now.
  2. Put sweep-jobs on a timer (cron every 10 minutes, or a systemd timer).
  3. Look at why they fail, in that school's database: SELECT kind, status, attempts, left(last_error, 200) FROM background_jobs WHERE status <> 'done' ORDER BY id DESC LIMIT 20;. The usual cause is the mail or SMS account (above).
Check
The rows become done and the messages arrive.

A job "used up its retries"

You see
An alert job_exhausted_retries, or a failed job with 5 attempts.
Why

It failed five times; it is left so a person can look.

Fix

Fix the cause (its last_error), then give it more tries: UPDATE background_jobs SET attempts = 0, status = 'failed' WHERE id = …; and run sweep-jobs. For a receipt, staff can also just press Send on the receipt again.

Check
The job becomes done.

Stored secrets and the delivery key

A school's saved mail password / SMS token / Paystack key "is not saved" any more

You see
The Email & SMS or Online payments page shows a secret as not saved, though it was.
Why

Stored secrets are encrypted per school under BRIGHTSTARS_DELIVERY_KEY, or, if that is not set, a key derived from BRIGHTSTARS_SECRET. Changing whichever is in use without re-encrypting makes every stored secret unreadable.

Fix
  1. If you still have the old value: put it back, restart, and then rotate properly (next entry).
  2. If not: each school re-enters its secrets (nothing else is lost).
Check
The pages show the secrets as saved, and tests send.

Rotating the delivery key safely

You see
You need to change BRIGHTSTARS_DELIVERY_KEY (a leak, a policy).
Why

Every school's stored secrets must be re-encrypted under the new key before the setting changes.

Fix
  1. python -m control_plane rotate-delivery-key OLD NEW (or the console's {{ route('platform_settings_rotate_key') }}).
  2. Then set BRIGHTSTARS_DELIVERY_KEY=NEW on every server and restart. Never change the variable first.
Check
A school's test email still sends.

Alerts

Getting told when something degrades

You see
You want a message on your phone or in Slack when something goes wrong.
Why

Four things always log a warning ({{ file('core/alerting.py') }}): registry_unreachable, job_exhausted_retries, delivery_failure_burst (many failed sends for one school), and sign_in_refusal_streak (sign-in limits hit).

Fix

Set BRIGHTSTARS_ALERT_WEBHOOK to a URL that accepts a JSON POST (a Slack "Incoming Webhook" address works as is). Each alert is also posted there, without slowing the request.

Check
A test: sign in wrongly enough times from one address to trip the limit, and the alert arrives.
