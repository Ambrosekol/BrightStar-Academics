Day-two knowledge: how the running system behaves, and what to do when something needs attention.

Backups and moving a school

Each school is one PostgreSQL database plus one folder. That is the whole unit of backup, restore and relocation. Restoring one school never touches another. To move a school to another deployment, dump its database, copy tenants/<code>/, register it there, and point its address at the new server. The registry (which schools exist, their addresses, the platform team) is separate and needs its own backup.

python -m control_plane export-tenant CODE [--output DIR] ({{ file('control_plane/provisioning.py') }}, export_tenant_data) does the school's own half of this in one command: a plain-SQL pg_dump of its database, a copy of its uploads folder, and a README explaining how to bring both back elsewhere - what a school leaving is owed, without assembling it by hand. Needs pg_dump on the machine's own PATH.

By default every school shares one PostgreSQL role and connection pool; python -m control_plane create-db-role CODE [--rotate] creates (or, with --rotate, re-passwords) a role that owns exactly one school's own database, and set-db-url CODE URL is the separate, deliberate step that actually points the registry at it (a literal URL, or env:VARIABLE_NAME so a live password need not sit in the registry's own database).

Upgrading the software

  • The schema of a school is declared once, in {{ file('models/__init__.py') }} and siblings. On start, create_all() creates missing tables and a helper adds missing columns to existing ones ({{ file('app.py') }}, _add_missing_columns); the registry does the same in {{ file('control_plane/registry.py') }}. There are no migration scripts.
  • python app.py upgrades every registered school before serving. With many schools or several workers, run python -m control_plane upgrade as a deploy step instead, then start the workers. Upgrade a single school with upgrade <code>.
  • A new column must have a default (or be nullable) so existing rows are valid at once. The helper refuses a NOT NULL column with no default.
  • Removing a feature that owned tables: an upgrade drops such a table only when it is empty ({{ file('core/retired_tables.py') }}); one that still holds rows is kept and a warning says so. drop-retired-tables shows what is left, and --yes drops it for good.

Restarts and sign-outs

A restart signs everyone out, on purpose: the signing secret does not change, so without this a cookie would outlive every restart. Everyone meets the sign-in page with "The system was restarted, please sign in again". The exception is anyone in the middle of an exam: a candidate with an unfinished paper, a student with an unfinished test, examination, practice paper or quiz whose time has not run out. They carry on as if nothing happened. The exam clock keeps running while the server is off, so a paper whose time ran out during the restart is finished from the answers already saved.

The mechanism is the launch id ({{ file('control_plane/launch.py') }}). To sign everyone out without restarting, run python -m control_plane new-launch. If the registry cannot be read, or no launch was ever recorded, nobody is signed out.

Suspending a school

Suspending takes a school's portal offline for everyone. It takes effect within BRIGHTSTARS_REGISTRY_CACHE_SECONDS (default 10) on each worker, because host lookups are cached per worker. Data is untouched and returns on reactivation. A suspended school's address shows a designed "portal paused" page with HTTP 503.

Background jobs

Work that should not hold up a request - sending a receipt, a notice - runs as a durable, database-backed job ({{ file('core/jobs.py') }}), not a thread that dies with the process. A stuck job of one kind is opportunistically retried the next time something of the same kind is enqueued; a school quiet enough that nothing else would ever trigger that needs its own nudge, which python -m control_plane sweep-jobs [CODE] gives every stuck job of every kind, across one school or all of them - meant for a cron or systemd timer, with no new service to deploy or keep running.

Alerting ({{ file('core/alerting.py') }}) watches the log lines that mean something needs a look: the registry unreachable, a job that used up its retries, a burst of delivery failures for one school, a sign-in rate limit actually being hit. They always log; set BRIGHTSTARS_ALERT_WEBHOOK to also have each one post there (Slack's own incoming-webhook shape works as-is).

Rate limits

Sign-in (schools and console), password recovery and the email/WhatsApp test buttons allow a number of tries per stretch of time, for example 8 sign-ins per 5 minutes per address and username. The counts live in the registry (table rate_limits), so several workers or a restart cannot multiply or reset them. Each is a fixed window; only a hash of the key is stored. If the registry cannot be reached each worker counts in its own memory and logs a warning at most once a minute; nobody is locked out. A limit at the reverse proxy is still worthwhile, and behind a proxy set BRIGHTSTARS_TRUSTED_PROXIES so the application sees real visitor addresses (or every visitor shares one count).

Passwords

  • Whoever changes their own password stays signed in where they did it; every other browser signed in to that account is signed out. The same happens when an administrator resets someone's login, when an emailed reset link is used, and for a platform admin's password. It is judged from the stored hash, so it holds however the password changed.
  • Accounts created or reset by someone else start on a temporary password that must be replaced before anything else opens.

Uploaded files

Files under /static/uploads/... are not open to every signed-in account. Each folder has its own rule ({{ file('core/upload_access.py') }}); ownership is read from the database row that holds the file, and a refusal is a plain 404 so a file's existence is not confirmed. A school's logo and photographs are public; message attachments are never served there.

When things go wrong

SymptomLikely cause and what to do
A school shows "address not found"The hostname is not registered (or is registered to another school); check the school's page in the console. A platform host that is also registered to a school logs a warning at start: the platform wins, taking that school offline.
Everyone reports being signed outA restart, or new-launch. Expected.
Parents say they received nothingThe school has no email/WhatsApp set up and the deployment has no shared account; or the guardian's email or phone is missing on the student; or WhatsApp's 24-hour rule. The delivery log says which.
A school cannot be enteredThe entry ticket is single-use and short-lived: go back to the console and press Enter school again. If the school cannot be reached, the console says so.
Every visitor seems to share one sign-in limitBehind a proxy with BRIGHTSTARS_TRUSTED_PROXIES at 0.
"Cannot add NOT NULL column" at upgradeA model added a required column with no default. Give it a default.
A receipt or notice never seems to sendRun sweep-jobs [CODE] to give it another try at once rather than waiting for ordinary traffic to trigger the opportunistic retry; if it keeps failing, the job's own log line explains why, and enough failures in a row raise an alert if BRIGHTSTARS_ALERT_WEBHOOK is set.
