Every request is matched to a school by the address it was sent to (the Host header) and nothing else ({{ file('control_plane/resolver.py') }}). So most "the site is wrong" problems are really "the address is wrong", and they are quick to find. Three questions settle almost all of them:

  1. Does the address reach this server at all? curl -s https://ADDRESS/health answers {"status":"ok"} on every address that reaches the application, school or not.
  2. Is the address registered? python -m control_plane list shows every school with its addresses.
  3. Is the school active? The same list, or the school's page in the console, shows its status.

The pages people see instead of a school

"We couldn't find that address." (Address not found, 404)

You see
A page titled "We couldn't find that address." with "The address you asked for is not registered with Brightstars Academics."
Why

The address reached the server, but no school has it: it was typed wrongly, the school's own domain was never added, it was removed, or the school was deleted. It also appears for plain localhost in development, where the page adds the console's address and the shape of a school's.

Fix
  1. Check the spelling against python -m control_plane list.
  2. A school's own domain (portal.theschool.example): add it on the school's page in the console ({{ route('platform_school_domains') }}) or with python -m control_plane add-domain CODE portal.theschool.example.
  3. If every school shows this at once: the application is reading the wrong (or an empty) registry. Check BRIGHTSTARS_PLATFORM_DB points at the real one; see {{ page('manual-startup', "It won't start, or a deploy failed") }}.
  4. If it shows for the issued address CODE.<portal domain>: check BRIGHTSTARS_PORTAL_DOMAIN is the domain you issued addresses under. Changing it later does not move existing addresses.
Check
The school's sign-in page opens at that address.

"This portal is temporarily unavailable." (Portal paused, 503)

You see
"Portal paused · This portal is temporarily unavailable. · Nothing has been lost."
Why

The school is suspended. Its data is untouched; everyone (staff, parents, students) is kept out until it is reactivated.

Fix

If it should be open: reactivate it on its console page ({{ route('platform_school_status') }}) or with python -m control_plane activate CODE. It takes effect within BRIGHTSTARS_REGISTRY_CACHE_SECONDS (10 by default) on every worker. To find out who suspended it and why, read the activity log ({{ route('platform_activity') }}).

Check
The sign-in page opens within a few seconds.

"There's nothing at this address." (Page not found)

You see
"Page not found · There's nothing at this address."
Why

The address belongs to the platform console (a BRIGHTSTARS_PLATFORM_HOSTS name) but the page is a school page; or a school address was asked for /school/… (schools have no public website). School pages never open on the console's address, and the console never opens on a school's.

Fix

Use the school's own address for school pages, and the platform host for /platform, /docs and /marketing.

Check
The page opens on the right address.

The documentation (these pages) answers 404 for an admin

You see
A platform admin signed in to the console gets "Page not found" at /docs.
Why

/docs is only for platform admins given access. Everyone else gets the same 404 as an address that does not exist, so its existence is not revealed.

Fix

The super admin grants it on the Team page ({{ route('platform_team') }}), per admin.

Check
The admin opens /docs.

DNS, a school's own domain and TLS

A school's own domain does not open the portal

You see
The browser cannot find the site, shows a certificate warning, or shows "Address not found".
Why

Three separate things must all be true: the domain is registered for the school here, the school's DNS points at your server, and your proxy has a certificate for it.

Fix
  1. Registered? It must appear under the school in python -m control_plane list. If not, add it (see above).
  2. DNS? dig +short portal.theschool.example must show a CNAME to the school's issued address (CODE.<portal domain>). The exact record is shown on the school's console page. DNS changes can take up to the record's TTL to spread.
  3. Certificate? Your proxy needs a certificate for the domain (Caddy and certbot can fetch one automatically once DNS points at you).
  4. Host passed through? The proxy must send the original Host header (nginx: proxy_set_header Host $host;). If it sends its own, every school answers "Address not found".
Check
curl -sI https://portal.theschool.example/login returns 200.

Browsers warn the certificate is not valid

You see
"Your connection is not private" / NET::ERR_CERT_COMMON_NAME_INVALID / expired.
Why

TLS is done by your reverse proxy, not by the application. The certificate does not cover the name, or it expired.

Fix
  • Issued addresses: use a wildcard certificate for *.<portal domain> (needs a DNS challenge).
  • Schools' own domains: one certificate each (or let Caddy's on-demand TLS fetch them).
  • Expired: renew (sudo certbot renew) and reload the proxy. Set up automatic renewal.
Check
echo | openssl s_client -connect HOST:443 -servername HOST 2>/dev/null | openssl x509 -noout -dates -subject shows a current certificate for the name.

The reverse proxy

The activity log shows the same address for everyone, or everyone hits "Too many sign-in attempts"

You see
Every entry in the activity log has the proxy's address (often 127.0.0.1); sign-in limits trip for a whole school at once.
Why

Behind a proxy, every connection comes from the proxy. Unless told how many proxies to trust, the application (rightly) ignores X-Forwarded-For, so everyone shares one address and one sign-in allowance.

Fix
  1. Set BRIGHTSTARS_TRUSTED_PROXIES to how many proxies of yours a request passes (1 for one nginx/Caddy; 2 with a load balancer in front). Restart.
  2. Make sure the proxy sends X-Forwarded-For and X-Forwarded-Proto (nginx: proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $scheme;).
Check
New activity-log entries show real visitor addresses.

Too high a number lets a visitor forge their own address (and dodge the sign-in limits). Count only proxies you run.

Links in emails, or "Enter school", use http:// instead of https://

You see
A password-reset email or the console's "Enter school" goes to http://….
Why

The proxy terminates TLS and talks plain HTTP to the application; without trusting it, the application believes the request was http.

Fix

Same as above: BRIGHTSTARS_TRUSTED_PROXIES and X-Forwarded-Proto.

Check
A new reset email's link starts with https://.

Large uploads fail with "413 Request Entity Too Large" from nginx

You see
A plain nginx page "413 Request Entity Too Large", not the application's own explanation.
Why

nginx refuses the upload before the application sees it (its default limit is 1 MB).

Fix

Set client_max_body_size 20m; (at least as large as the largest school branding upload) in the nginx server block, and reload nginx. The application then applies its own, explained limits.

Check
A large photo uploads, or is refused with the application's own message naming the limit.

"502 Bad Gateway" or "504 Gateway Timeout"

You see
The proxy's own 502/504 page.
Why

502: the application is not running or not listening where the proxy expects. 504: it is running but a request took longer than the proxy waits.

Fix
  1. 502: systemctl status brightstars; if it is down, see {{ page('manual-startup', "It won't start, or a deploy failed") }}. Check the proxy's upstream address matches gunicorn's -b.
  2. 504: find the slow page in the log; usually a database that is out of connections or very slow (see {{ page('manual-database', 'Databases and connections') }}). Raise the proxy's timeout (proxy_read_timeout 120s;) and gunicorn's --timeout only for genuinely long work such as a class's report-card PDF.
Check
curl -s http://127.0.0.1:8000/health on the server answers, and the page loads through the proxy.
