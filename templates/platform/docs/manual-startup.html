The application checks its own settings as it starts, and refuses to start rather than run in a state that would be unsafe or silently wrong. That is good news when something is wrong: the message it prints says exactly which setting, and this page says what to do about it. Read the last lines of the output (or of your service's log, for example journalctl -u beacon -n 50 under systemd): the cause is the final RuntimeError or ProvisioningError line.

Every setting mentioned here is explained in full, with its default and the symptom when it is wrong, on {{ page('manual-env', 'Every environment variable') }}. Settings are read from the real environment first and then from .env in the project folder; a variable set in the environment always wins over .env.

The application refuses to start

"This looks like a real deployment … but BEACON_ENV is …, not production"

You see
RuntimeError: This looks like a real deployment (it is running under a production web server …; its portal domain is …; a reverse proxy is set in front of it …) but BEACON_ENV is "development", not "production".
Why

Outside production the application drops protections a public server needs: cookies are not marked Secure, there is no HSTS, the strong-secret check is skipped, and a school's mail server may point at a private address. So when the start looks like a real deployment (it runs under gunicorn, waitress or uwsgi; its BEACON_PORTAL_DOMAIN is a real domain; or BEACON_TRUSTED_PROXIES is above 0), it will not start unless BEACON_ENV=production (refuse_unsafe_environment in {{ file('app.py') }}). The message lists which of those it saw.

Fix
  1. On a real server: set BEACON_ENV=production (in the service's environment or .env), and restart.
  2. On a developer machine that tripped it by mistake: use BEACON_PORTAL_DOMAIN=localhost (or a .test / .local name), BEACON_TRUSTED_PROXIES=0, and run python app.py rather than gunicorn.
  3. Only on a staging server that genuinely must run as development: BEACON_ALLOW_NON_PRODUCTION=1. Never on a real deployment.
Check
The application starts, and on a real deployment every response carries a Strict-Transport-Security header.

"BEACON_SECRET must be set to a strong secret (at least 32 characters) in production."

You see
RuntimeError: BEACON_SECRET must be set to a strong secret (at least 32 characters) in production.
Why

The secret signs every sign-in cookie. A short or missing secret in production would let someone forge a sign-in.

Fix
  1. Generate one: python -c "import secrets; print(secrets.token_hex(32))"
  2. Set it as BEACON_SECRET on every server of the deployment (they must share it, or a sign-in made on one is refused on another).
  3. Restart. Everyone is signed out once, because the old cookies were signed with the old secret.
Check
The application starts, and you can sign in and stay signed in across pages.

Changing BEACON_SECRET also changes the default key schools' stored mail, SMS and Paystack secrets are encrypted under, unless BEACON_DELIVERY_KEY is set. Set BEACON_DELIVERY_KEY before you ever rotate the secret, or every school must re-enter those secrets. See {{ page('manual-messaging', 'Email, SMS, background jobs and alerts') }}.

"BEACON_PLATFORM_DB is not set"

You see
RuntimeError: BEACON_PLATFORM_DB is not set. It is the PostgreSQL URL of the platform registry …
Why

The registry database records which schools exist and where their databases are. It has no default on purpose: a wrong guess would create an empty registry and every school would look as if it did not exist.

Fix
  1. Set BEACON_PLATFORM_DB=postgresql+psycopg://USER:PASSWORD@HOST:5432/beacon_platform (the +psycopg part is required).
  2. On a new server, run python -m control_plane init once to create it.
  3. On an existing deployment, make sure it points at the same registry as before (check the database name). Pointing at a new, empty one makes every school answer "Address not found".
Check
python -m control_plane list prints your schools.

"Could not reach PostgreSQL to create the platform registry"

You see
RuntimeError: Could not reach PostgreSQL to create the platform registry: … (connection refused / password authentication failed / could not translate host name …)
Why

The URL in BEACON_PLATFORM_DB cannot be reached or its credentials are wrong. The text after the colon is PostgreSQL's own reason.

Fix
  • connection refused / timeout: PostgreSQL is not running, or a firewall blocks port 5432. Start it; on a managed database, allow your server's IP address.
  • password authentication failed: wrong user or password in the URL. A password with @, : or / must be URL-encoded (@ becomes %40).
  • database "postgres" does not exist: the provider has no maintenance database by that name (Aiven calls it defaultdb). Set BEACON_PG_MAINTENANCE_DB to one that exists.
  • permission denied to create database: the role needs CREATEDB, or create the registry database by hand and keep the URL pointing at it.
  • SSL required: add ?sslmode=require to the URL.
Check
psql "<the same URL without +psycopg>" -c "select 1" works from the server.

"BEACON_TRUSTED_PROXIES is …, which is not a number this application can use"

You see
RuntimeError: BEACON_TRUSTED_PROXIES is "lots", which is not a number this application can use …
Why

It must be a whole number from 0 to 5: how many reverse proxies of yours stand in front of the application.

Fix

Set it to 0 with no proxy, 1 behind a single nginx or Caddy, 2 with a load balancer in front of that. See {{ page('manual-addresses', 'Addresses, domains and proxies') }}.

Check
The application starts; the activity log shows visitors' real addresses, not the proxy's.

"BEACON_STORAGE_BACKEND is …" or "BEACON_S3_… is not set"

You see
RuntimeError: BEACON_STORAGE_BACKEND is "aws", but only "local" or "s3" is understood. — or — BEACON_S3_BUCKET is not set. Required when BEACON_STORAGE_BACKEND=s3.
Why

Schools' files (uploads, question banks, numbering rules) are kept either in a local folder or in an S3-compatible bucket. With s3, the bucket and both keys are required ({{ file('control_plane/config.py') }}).

Fix
  1. Use exactly local or s3.
  2. For s3, set BEACON_S3_BUCKET, BEACON_S3_ACCESS_KEY_ID, BEACON_S3_SECRET_ACCESS_KEY, and for a provider that is not AWS (Cloudflare R2, Backblaze B2, DigitalOcean Spaces, MinIO) BEACON_S3_ENDPOINT_URL (and usually BEACON_S3_REGION=auto).
Check
A school's logo shows on its sign-in page. If it does not, see {{ page('manual-files', 'Files, uploads, storage and imports') }}.

"Cannot add NOT NULL column … with no default"

You see
RuntimeError: Cannot add NOT NULL column <table>.<column> …
Why

New columns are added to existing databases automatically at start-up and on upgrade. A column that is nullable=False with no default cannot be added to a table that already has rows. This is a code mistake in a model, not a server problem.

Fix

In the model (under models/ or {{ file('control_plane/models.py') }}), give the column a default= and a server_default=, or make it nullable. Deploy again. See {{ page('manual-code', 'Finding and fixing it in the code') }}.

Check
python -m control_plane upgrade finishes without errors.

ModuleNotFoundError: No module named …

You see
ModuleNotFoundError: No module named 'openpyxl' (or flask, psycopg, boto3, cryptography, …)
Why

The server's Python environment is missing a package from requirements.txt, usually because a deploy pulled new code but did not install its new requirements.

Fix
  1. Activate the deployment's virtual environment (source venv/bin/activate).
  2. pip install -r requirements.txt
  3. Restart the application.
Check
python -c "import app" runs without an error from the project folder.

openpyxl and defusedxml are only needed for Excel imports. If they are missing the application still starts and CSV imports still work, but an Excel file is refused with "Excel files cannot be read on this server yet".

"Address already in use"

You see
OSError: [Errno 98] Address already in use
Why

Another process (often the previous copy of the application that did not stop) is listening on the port.

Fix
  1. Find it: sudo ss -ltnp | grep :8000 (or :5000 for python app.py).
  2. Stop it through your service manager (sudo systemctl stop beacon), or kill the stray process.
  3. Start again. For the built-in server, PORT chooses another port.
Check
curl -s http://127.0.0.1:8000/health answers {"status":"ok"}.

Deploys and upgrades

The safe order for every deploy

You see
A deploy is due, or the last one left something half done.
Why

Code, packages and the databases' shape have to move together. Doing them in this order means no request ever meets code that expects a column the database does not have yet.

Fix
  1. Pull the new code.
  2. pip install -r requirements.txt
  3. python tests/current/run_current.py (fast; no database needed) to catch a broken checkout.
  4. python -m control_plane upgrade: brings every school's database and the registry up to date, then records a new launch (everyone signs in again, except people sitting an exam).
  5. Restart the application servers (sudo systemctl restart beacon).
  6. Check: /health answers, a school's sign-in page opens, you can sign in to the console.
Check
The sign-in page footer shows the new version (the newest release in release_notes.json).

"upgrade" fails for one school

You see
The upgrade output names a school and an error (cannot connect, permission denied, a column problem).
Why

Each school has its own database, upgraded one by one ({{ file('control_plane/provisioning.py') }}). One unreachable or broken school does not stop the others, but it stays behind until fixed.

Fix
  1. Read the error for that school. Cannot connect: see {{ page('manual-database', 'Databases and connections') }} (is its database URL right? does its role still exist?).
  2. Fix it, then upgrade just that school: python -m control_plane upgrade CODE, or {{ route('platform_settings_upgrade') }} in the console.
Check
The school's portal opens and its pages that use new features work.

A page errors with "column … does not exist" after a deploy

You see
The 500 error page, and in the log: psycopg.errors.UndefinedColumn: column … does not exist (or UndefinedTable: relation … does not exist).
Why

The code was updated but that school's database was not upgraded yet, so a new column or table is missing.

Fix

Run python -m control_plane upgrade (all schools) or upgrade CODE (one). Nothing needs to be restarted afterwards.

Check
The page opens. On a developer machine, tests/current/test_models_match_db.py stops reporting "model/schema drift".

Rolling a bad deploy back

You see
A deploy broke something important and there is no quick fix.
Why

Schema changes here only ever add tables and columns, so older code still runs against an upgraded database: rolling back the code is safe.

Fix
  1. git checkout <the previous good commit> (find it with git log --oneline).
  2. pip install -r requirements.txt (the older list).
  3. Restart. Do not run anything that drops tables.
  4. Fix forward on a branch, test, and deploy again.
Check
The broken pages work again. Data written by the newer version in new columns is kept, just unused, until you deploy forward.

Restarts

Everyone was signed out after a restart

You see
"The system was restarted, please sign in again."
Why

On purpose. Every start (and every upgrade) records a new launch id ({{ file('control_plane/launch.py') }}); a sign-in from before it ends, so a stolen cookie cannot outlive a restart. People sitting an exam are kept signed in and carry on.

Fix

Nothing to fix. To avoid surprising staff, restart outside school hours. To sign everyone out deliberately without restarting: python -m control_plane new-launch or {{ route('platform_settings_new_launch') }}.

Check
People can sign in again straight away.

The service keeps restarting

You see
systemctl status beacon shows it starting and stopping again; gunicorn logs "Worker failed to boot".
Why

A start-up check fails every time (one of the messages above), or a worker crashes on import.

Fix
  1. Stop the service so the log stops scrolling: sudo systemctl stop beacon.
  2. Run the import by hand, as the service user, in the project folder, with the same environment: python -c "import app". The real error appears.
  3. Fix it from the matching entry on this page, then start the service.
Check
systemctl status beacon stays "active (running)".

After deploying the design studios

"relation "report_card_designs" does not exist" (or "receipt_designs")

You see
A server error opening a report card, a receipt or a studio after a deploy; the log names one of those tables.
Why

The deploy added tables ({{ table('report_card_designs') }}, {{ table('report_card_design_versions') }}, {{ table('receipt_designs') }}, {{ table('receipt_design_versions') }}) and the schools' databases were not upgraded.

Fix

Run python -m control_plane upgrade (it creates the missing tables in every school), then restart.

Check
The pages open.

Report cards and receipts are slow to download

You see
A class's report cards take several seconds; CPU high while PDFs are made.
Why

Without rl_accel (requirements.txt), reportlab uses its slower pure-Python code: about a quarter more CPU for every PDF. PDFs are written without ASCII85 ({{ file('core/pdf_setup.py') }}).

Fix

Run pip install -r requirements.txt on every server, then restart. Check with python -c "import rl_accel".

Check
The import succeeds; a class PDF is faster.
