Two folders, two jobs. tests/current/ is fast and runs after every change. tests/verification/ drives the real application against real PostgreSQL and is run when a change touches something the fast tests cannot see. Between them they are the reason a change to one school's feature does not silently break another school's.

The contract suite: tests/current/

python tests/current/run_current.py

Source-level checks of architecture, security, the assessment flow, roles and multi-tenancy rules. It needs no database, except that the schema-drift check compares the models with the first registered school when one is reachable (and is skipped when none is).

The end-to-end scripts: tests/verification/

Each script creates its own throwaway databases (bs_test_*), runs, and drops them, and clears any left by a crashed run. They never touch real data. They need PostgreSQL reachable through your .env and are run by hand; each prints PASS/FAIL lines and a total. Run the ones for the area you changed, plus the two big ones below before a release.

How the scripts work

  • {{ file('tests/verification/_pg.py') }} sets up the throwaway databases. It gives each run a unique prefix and a database-name template with a literal {slug}, so every school under test gets its own database. (An earlier bug percent-encoded those braces, so every test school silently shared one database and isolation checks passed or failed for the wrong reasons; keep that in mind when touching it.)
  • The scripts call the Flask application in process through its test client, with hostnames like posts.portal.test, so the real resolver, real sessions and real CSRF are all in play.
  • The outside world is stood in for at the last step. A fake SMTP connection and a fake urlopen catch email and WhatsApp, so the real sending code (including building a PDF) runs but nothing leaves the machine.
  • They set A.app.config['BACKGROUND_INLINE'] = True so messages to parents are sent at once and can be inspected ({{ file('core/jobs.py') }}).
  • An Actor is one browser with its own cookies; check(name, ok, detail) records a result; sql(...)/one(...) read the school's database directly to confirm a row was written.

The coverage guard

A query PostgreSQL rejects is easiest to miss in a form submission, and pages that only load can look fine. So the fast suite imports the application and compares its URL map with tests/verification/pg_posts_coverage.py: every route that accepts POST, PUT, PATCH or DELETE must be in EXERCISED (the big script really submits it) or EXEMPT (with a written reason). The big script also checks the other direction: what it actually submitted must equal EXERCISED. So a new route cannot ship untested on PostgreSQL, and the list cannot claim more than the script does.

Writing a check

# in write_paths_pg_posts.py, in the section for the area
op.post(f"/admin/school/notices/new", {"title": "Sports day", "body": "Friday"})
check("a notice was saved", count("school_notices", "title = :t", t="Sports day") == 1)

Then add the route pattern (as Flask writes it, with converters like <int:notice_id>) to EXERCISED. Prefer asserting on the database and on what a person would see, not on incidental wording.

Known state of the suites

All suites pass except one that needs Chrome (write_paths_candidate_results.py) on a machine without it. If a script fails at its very start with "three schools were created" or similar, check the database-name template in {{ file('tests/verification/_pg.py') }} first.
