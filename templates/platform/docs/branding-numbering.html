A school's identity

Each school has its own name, motto, tagline, phone, email, address, logo, two brand colours and up to eight sign-in photographs. They are set on the platform's Create a school form, so nobody ever sees a portal wearing another school's name, and can be changed afterwards by platform operators (from the school's page in the console) or by the school's own administrators with {{ perm('branding.manage') }} ({{ route('admin_school_branding') }}).

  • Where it is kept. As key/value rows in {{ table('school_public_settings') }} (read by {{ file('core/public_settings.py') }}); the school's own row is in {{ table('schools') }}. Files (logo, photos) are under the school's uploads/branding/, which is the one folder anyone may open, because the sign-in page needs it.
  • How code reads it. Always through school_brand() and school_name() ({{ file('core/branding.py') }}), and in templates through school_brand. Never hard-code a school's name, motto or logo. A contract test fails the build on any occurrence.
  • Colours. {{ file('core/theme.py') }} is deliberately free of Flask and the database. A colour is accepted only as #rrggbb and written into a page only as that normalised value, because it goes inside a <style> block: anything looser would let a school's settings inject CSS into its own users' pages. Both colours sit behind white text, so a colour with less than 4.5:1 contrast against white is refused.
  • How colours reach the pages. An after_request hook (apply_school_theme in {{ file('app.py') }}) injects :root{--navy:...;--blue:...} into every school HTML response; the stylesheets read those variables. The Brightstars logo never appears on a school's portal, only on the platform's own pages.

The school interface's design system

All school-facing pages use one design system, static/school-ui.css: tokens for the school's colours (--brand, --brand-dark, --brand-accent), a warm-grey surface scale, type, spacing, radii, the focus ring, and the components built on them: the navigation rail, workspace home, sign-in and password pages. Use the tokens; do not add new colours or sizes. Fonts are self-hosted in static/fonts/ (Public Sans for text, Newsreader for titles and the school's name, IBM Plex Mono for codes only), because the Content-Security-Policy allows no outside font. Who sees which menu item is one list in {{ tpl('admin_base.html') }}; icons come from {{ tpl('includes/_nav_icons.html') }}. Sign-in and password pages extend {{ tpl('auth_base.html') }}.

The platform console, this documentation and the marketing page have their own look (static/platform.css, static/docs.css, static/marketing.css). Do not mix the two sets.

Uploads

Every picture upload goes through one hardened saver in {{ file('core/uploads.py') }}: type and size are checked, the content is verified as a real image, the file is renamed with random characters, and it is stored only in the school's own folder. People are always told the limit: every file box prints the real limit under itself, static/upload-limit.js refuses a too-large or wrong-type file beside the box before anything is sent, and the server gives the same explanation (the file's name, its size and the limit) if the script is off. The limits are BRIGHTSTARS_MAX_UPLOAD_BYTES (one image; the default is a few megabytes) and BRIGHTSTARS_MAX_REQUEST_BYTES (a whole request, larger still); pages that take a logo plus a gallery raise the request limit to fit. See the {{ page('reference-config', 'configuration reference') }} for the exact defaults.

Who may open a stored file is decided folder by folder in {{ file('core/upload_access.py') }}; see {{ page('security', 'Security model') }}.

Numbering: how a school writes its people's codes

A school chooses how candidate codes and student numbers look. Platform operators set this as a pattern on the console, both when creating the school and later on its page:

{% raw %}{school}-{year}-{seq:4}{% endraw %}      →   ABC-2026-0007

Placeholders include the year, month, the school's code, the class, a running number with a width and range, and random letters or digits. The full table is on the console's numbering editor ({{ tpl('platform/_numbering.html') }}). Important rules:

  • A pattern needs a seq or a random part, and at most one seq. Unknown placeholders, unbalanced braces, forbidden characters and patterns over 80 characters are refused with a message naming the problem and its position.
  • seq counts within its siblings. The next number is one more than the biggest already used by a code with the same text in every other part, so the count restarts by itself each year if the year is in the pattern, per class if the class is, and never if neither is.
  • A finished candidate code is 3 to 40 characters (letters, digits, . _ -); a student number is 1 to 40 and may also contain /. A pattern that could produce a code failing these is refused when it is saved.
  • Codes already issued never change. A new pattern applies only to codes made after it is saved.
  • Student numbers: the platform's running number ({{ file('services/student_number_generator.py') }}) stays the source of the sequence and of the ledger ({{ table('student_number_allocations') }}) that stops a number being issued twice; the pattern only decides how the number is written.

Nothing typed is ever run. {{ file('core/numbering_pattern.py') }} reads a pattern: it splits it into pieces, checks each against a fixed list, and fills it in. There is no eval, exec, import or template engine anywhere near it. The rules are stored as data in tenants/<code>/numbering.json ({{ file('core/numbering.py') }}), read and written whole and atomically, and a corrupt file is refused with a plain message and never silently replaced. An earlier design used a Python file per school; it was removed because being able to set numbering would have meant being able to run code on a server that reaches every school's database.

Every save is recorded in the platform audit log with the old and the new pattern.
