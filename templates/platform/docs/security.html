A school holds children's names, photographs, results and fees. The security design is built around one worst case: one school seeing another's data. Most controls below serve that, and the rest keep the platform's own operators honest.

Headers and cookies

Every response gets (in apply_security_headers, {{ file('app.py') }}): X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: same-origin (the application does read its own Referer for "go back"), a restrictive Permissions-Policy, HSTS in production, and this Content-Security-Policy:

default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline';
script-src 'self' 'nonce-<random per request>'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'

Consequences you will hit. No external fonts, scripts, images or stylesheets: everything is self-hosted, which is why fonts live in static/fonts/. script-src allows no inline script at all except one carrying that request's own nonce (csp_nonce(), {{ file('app.py') }}): every onclick/onchange/onsubmit attribute a template used to carry was moved to delegated, data-*-driven listeners in {{ file('static/interactions.js') }}, since an inline event-handler attribute is exactly as dangerous to CSP as an inline <script> block. style-src keeps 'unsafe-inline' deliberately: a school's own brand colours are already restricted to #rrggbb before they reach a <style> block, where a nonce would buy nothing. Password-reset pages are never cached and send no referrer.

Secrets: what to protect

  • BRIGHTSTARS_SECRET signs every session cookie. Anyone with it can forge a sign-in for any school. Keep it out of source control and logs; rotate it only knowing everyone will be signed out (and that, without BRIGHTSTARS_DELIVERY_KEY, saved school credentials become unreadable).
  • BRIGHTSTARS_PLATFORM_DB holds a database credential that can create databases. Store it as a secret.
  • BRIGHTSTARS_DELIVERY_KEY can be changed on a calendar, safely: python -m control_plane rotate-delivery-key OLD NEW [CODE] ({{ file('core/secrets_rotation.py') }}) decrypts every school's own mail password, WhatsApp token and Paystack secret key under the old key and re-encrypts them under the new one first, school by school, so the environment variable itself is only ever changed once every school shows nothing unreadable - never the other way round.
  • Flask sessions are signed, not encrypted: the person can read their own cookie. Never store anything in a session that they must not see.
  • Never log a password, token, or a school's stored credential. Audit entries record which fields changed, not their values.

What it does not do

Honest limits, so nobody assumes more than exists:

  • No two-factor authentication for any account, including platform admins.
  • Databases are not encrypted per school beyond stored delivery credentials; rely on disk and PostgreSQL-level encryption and access control.
  • A shared PostgreSQL role, by default. Out of the box the same role connects to every school's database; a compromised application process can read every school. Isolation is by design and by test, not by database privileges. A separate, database-owning role per school is a command away rather than a manual DBA task (python -m control_plane create-db-role CODE, {{ file('control_plane/provisioning.py') }}) but is opt-in, not the default, and pointing a school at it (set-db-url) is a deliberate second step.

Each is a candidate for the hardening list in {{ page('recommendations', 'Recommendations') }}.
