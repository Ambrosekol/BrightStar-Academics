# Directory cleanup — 2026-09-16

The project root had accumulated 57 top-level entries across several phases of
development with no version control. This records what was removed and moved,
and how each decision was verified, so the reasoning survives even though the
files don't.

## Deleted — dead code and data, verified unreferenced in both this tree and the Phase 13 source it was merged from

* `static/css/admin.css` — a duplicate of `static/admin.css` that no template
  ever linked (`url_for('static', filename='admin.css')` resolves to the one at
  the top level).
* 8 templates never reached by any route: `admin_login.html`,
  `admin_practice_tests.html`, `admin_school_module.html`,
  `admin_school_settings.html`, `entrance_config.html`,
  `finance_assessment_bulk.html`, `public_index.html`, and the explicitly named
  `admin_candidate_result_print_BACKUP.html`. `review.html` looked similarly
  orphaned but was kept — `security/verify_candidate_result_static.py` reads it
  directly by path to check that a candidate's result page never leaks a raw
  score, an invariant not covered anywhere else.
* 6 raw question-bank JSON files in `data/` that key their identity as
  `bank_id` rather than `id`. `load_banks()` requires `b.get('id')`, so these
  were never loaded — silently shadowed by their `_PRODUCTION_BANK` (or, for
  Mathematics, `_PRODUCTION_BANK_FINAL`) counterparts, which do carry `id` and
  are the ones actually serving exams. Confirmed by loading every bank before
  and after: the same 6 real banks, same question counts.
* `data_BEFORE_SIX_BANK_LOAD/` — a manual backup of `data/` predating the
  bank set above, superseded and unreferenced.
* `static/generated/` — cached result-image PNGs from `_chrome_result_png()`.
  The function recreates this directory with `mkdir()` on first use, so
  deleting it is free.
* An empty `instance/` directory (Flask's default instance-relative-config
  folder; this app doesn't use instance-relative paths).
* All `__pycache__/` directories outside `venv/`.

## Deleted — migration safety-net backups, on explicit confirmation

The SQLAlchemy/Phase 13 merge (see `PHASE13_MERGE_NOTES.md`) kept backups as
its only rollback path in a repository with no version control. Once that
migration was verified stable across route parity, RBAC equivalence and the
write-path test suites, these were removed on the user's explicit
confirmation rather than left as permanent dead weight:

* `app_before_sqlalchemy_migration.py`
* `app_before_admin_security_phase_a.py`
* `cbt_before_sqlalchemy_migration.db`
* `BACKUP_BEFORE_PHASE13_MERGE_20260916_141232/`

## Moved, not deleted

* `verify_phase3h.py` (root) → `tests/legacy/verify_phase3h.py` — no duplicate
  existed there yet; it belongs with its siblings under the same documented
  convention. Its `ROOT = Path(__file__).resolve().parent` assumption broke
  when moved (it now pointed at `tests/legacy/` instead of the project root),
  so it was corrected to `.parents[2]` and re-verified to run.
* `verify_admin_security.py` (root) → `tests/verification/verify_admin_security.py`.
  This one is *not* a duplicate of `tests/legacy/verify_admin_security.py`,
  which still calls the removed `app.db()` connection factory and is kept
  there deliberately as the forensic record of Phase A. The root copy was
  rewritten for SQLAlchemy in the Phase 13 merge and is current, working
  tooling — it belongs alongside the rest of `tests/verification/`, not with
  the retired scripts in `tests/legacy/`. Its bare `import app` assumed the
  project root was already on `sys.path` (true when run from the root, which
  is where it used to live); a `sys.path.insert` + `os.chdir` was added so it
  works from any invocation location, matching its new siblings.
* ~20 historical `PHASE*.md` / `.txt` files, `ADMIN_SECURITY_ARCHITECTURE.md`,
  `PHASE_A_ADMIN_SECURITY_README.md`, `SECURITY_RESULT_ACCESS_FIX.md`, and
  `START_HERE_TEST.txt` → `docs/phase-history/` (this folder). Nothing in
  `tests/` or `app.py` referenced any of them by path. `README.md` and
  `PHASE13_MERGE_NOTES.md` stayed at the root — the former is the project's
  front door regardless of how stale its content is, the latter documents the
  current state of the codebase rather than a closed phase.

## Left alone, and why

* **`venv/`** — regenerable via `pip install -r requirements.txt`, but
  deleting it would leave `python app.py` unable to run until reinstalled.
  Outside the scope of "won't have any issues to the project."
* **`security/`** — `test_rules.py` still passes. `verify_candidate_result_static.py`
  fails one of six checks (a stale string match on wording that has since
  changed), but the other five, together with `review.html`, are the only
  place the "candidate result page carries no score" invariant is checked at
  all. Retiring it was out of scope for a directory cleanup.
* **`deployment/`** — Windows server-startup and firewall scripts, referenced
  from `README.md`; these are operational tooling, not clutter.
* **`docs/`** (the rest of it) — `tests/current/test_architecture_contract.py`
  and `test_assessment_contract.py` read `docs/BASELINE_SHA256.txt` and files
  under `docs/architecture/` directly; this is load-bearing for the test
  suite.

## Noted but not acted on

* `templates/public_admissions.html` references `img/school-building.jpg`,
  which does not exist (`static/img/` isn't a directory at all — the school's
  photos live under `static/images/school/`). This is a live bug on the public
  admissions page, not a leftover file; fixing it needs to know which actual
  image was intended, so it wasn't guessed at here.
* `static/images/school/IMG_8999.JPG.jpg` is not linked from any template.
  Unlike the dead code above, this is content — a real photo someone
  uploaded — so it was left in place rather than treated as clutter.
* `START_HERE_TEST.txt` (now archived above) states the Super Admin password
  is `admin123`. `PHASE3G_SUPERADMIN_CREDENTIALS_HARDENING.md` (also archived)
  indicates that hardcoded default was deliberately removed in favour of a
  random bootstrap password printed once at first `init_db()`. The `.txt` file
  was never updated after that change and is actively wrong; it's preserved
  as-is for the historical record, but don't follow it.
