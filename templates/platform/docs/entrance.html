Entrance examinations are how a school admits new students: candidates register (or are registered), sit timed computer-based papers, and are ranked. The exam engine is older than the rest of the school portal and everything else (tests, examinations) was modelled on its attempt-and-grading design. Shared logic is in {{ file('core/entrance.py') }}; the admin side is {{ file('blueprints/entrance/routes.py') }}; candidates' own side is {{ file('blueprints/candidate_portal/routes.py') }}.

Question banks

A school's banks are JSON files in its own folder, tenants/<code>/data/ ({{ file('core/storage.py') }}), owned by the school. Copying the folder moves them; no school can read another's.

{
  "id": "starter_year7_mathematics",
  "name": "Mathematics ...",  "level": "...",  "subject": "Mathematics",
  "entry_group": "year7",     "duration_seconds": 3600,  "version": "1.0",
  "questions": [
    { "id": 1, "text": "...", "options": ["...", "...", "...", "..."], "answer": 1, "points": 1 }
  ]
}
  • A new school is not empty. Creating a school copies the platform's standard banks from starter_banks/ (six: Mathematics, English and General Knowledge for Year 7 and SSS 1; 255 questions written for the platform, naming no school). Nothing is ever overwritten. A contract test keeps the set free of any school's name.
  • A school can bring its own. Question Banks, Import from file takes a JSON file. It is checked strictly by {{ file('core/banks.py') }}: a size cap in the low megabytes, a safe id, a name, 1 to 500 questions, each with four different options and an answer, no picture paths. Everything wrong is listed at once, it is written only inside the school's own folder, replacing needs an explicit tick, and every import is audited. Permissions: {{ perm('question_banks.create') }}, {{ perm('question_banks.edit') }}.
  • Writes are atomic and checked so a crash never leaves half a bank ({{ file('blueprints/entrance/helpers.py') }}, save_bank). A bank can be locked during a live exam, which makes it refuse edits.
  • A question's order can be changed from the screen - an up/down button per question on {{ tpl('admin_bank.html') }}, each carrying the whole new order for that one swap (worked out once, server-side, in the template) to {{ route('admin_reorder') }}. Permission: {{ perm('questions.reorder') }}.
  • The subject of a bank is worked out from its fields (bank_subject) and its entry class from bank_entry_group. There are two entry groups: year7 ("Year 7 / JSS 1") and year10 ("Year 10 / SSS 1"); both names are always shown together, because schools use one or the other.

Making a bank a live paper

A bank is not an exam until it is configured ({{ table('entrance_bank_configs') }}): bank, entry group, subject, session, term, and how many questions to serve. Exactly one configuration is live per group, subject, session and term; activating one deactivates its rivals ({{ route('admin_entrance_config_activate') }}). One click sets up the standard papers for the current session.

A paper is always out of 100. The number of questions served must split 100 into whole hundredths (_valid_question_configuration): 20, 25, 40 and 50 work; 30 does not (3.33...). Marks are stored as decimals so a raw score is exact. A configuration already issued to a candidate is frozen: changing it would change the meaning of results already given.

{{ table('examinations') }} rows mirror the banks (sync_examinations) so an attempt has something to point at.

Candidates

  • Staff register a candidate ({{ route('admin_candidates') }}): name, target class, previous school, parent or guardian details, photograph. A candidate code and password are generated and shown once, on a printable sheet.
  • The target class maps to an entry group (normalize_entry_group), which decides which papers they must sit (required_papers_for_target): one paper per subject, in numbered slots ({{ table('candidate_papers') }}).
  • The code is written by the school's numbering pattern ({{ page('branding-numbering', 'Identity and numbering') }}).

The admissions funnel: candidate to student

Every active candidate who has attempted at least one paper is on the admissions waitlist ({{ route('admin_candidate_admissions') }}, {{ file('blueprints/entrance/admissions.py') }}), ranked by overall percentage; one who has never attempted anything does not appear at all. Two admission columns live directly on {{ table('candidates') }} rather than a separate table, since a candidate has at most one admission decision, ever: admission_status ('pending', 'admitted' or 'declined') and admitted_student_id.

  • Admitting ({{ route('admin_candidate_admit') }}) creates exactly what {{ route('admin_school_student_new') }} creates by hand — a {{ table('students') }} row, a {{ table('student_enrolments') }} row for the current session, and a login — through the same allocate_student_number and _provision_student_account either way, so an admitted candidate is indistinguishable from a student registered one at a time. The candidate's one-field candidate_name is split into first/middle/last as a starting guess on the form, correctable before confirming. If the candidate has a guardian email or phone on file and the box is left ticked, a {{ table('parent_accounts') }} row and a {{ table('parent_student_links') }} row are created too. Admitting is terminal: an admitted candidate can never be admitted again, declined, or reset.
  • Declining ({{ route('admin_candidate_decline') }}) takes a candidate off the waitlist with an optional note, and — unlike admitting — can be undone ({{ route('admin_candidate_admission_reset') }}).
  • Guarded by one permission, {{ perm('candidates.admit') }}, separate from {{ perm('candidates.view') }}: seeing the waitlist at all, not only deciding it, needs this permission. The Admissions Officer role preset carries it; nobody else does by default. A candidate route's scope is the pre-existing generic mechanism in admin_scope_for_request (a cid URL argument resolves to a 'class' scope of the candidate's own target_class), so an officer scoped to one entry level cannot act on the other's candidates.

Sitting a paper

  1. The candidate signs in and sees their dashboard ({{ route('candidate_dashboard') }}), never their scores.
  2. Start ({{ route('candidate_start_paper') }}) checks: the paper is theirs, its configuration is valid, no other paper is open, and they have not already taken it (unless staff granted a retake). Then one attempt is created with an expiry, and serve_count questions are drawn at random and frozen into {{ table('attempt_questions') }}.
  3. The exam page ({{ route('exam') }}) shows one question at a time with a countdown; each choice is saved immediately ({{ route('answer') }}). Time is enforced by the server.
  4. Submitting ({{ route('submit') }}) or running out of time grades the attempt from the frozen copy (grade in {{ file('core/entrance.py') }}).

Restarts. A candidate with an unfinished paper is exempt from the "restart signs everyone out" rule; they carry on, and the clock keeps running while the server is off. A paper whose time ran out during a restart is finished from the answers already saved.

A dropped connection is not the paper being over. The exam page's own script retries a save that fails over the network or gets an unexpected server error, a bounded number of times, before telling the candidate in plain words rather than losing the answer silently; only a definite refusal from the server (403 the session has ended, 410 time ran out) sends them to their result. {{ route('answer') }} is itself an upsert keyed on (attempt, question), so a retried save of the same answer is never a duplicate.

Staff controls: rankings, results, per-subject analytics, CSV/JSON export, a result image (drawn by headless Chrome, BRIGHTSTARS_CHROME), grant retake ({{ route('admin_grant_retake') }}, a one-use permission stored in {{ table('retake_grants') }}) and regrade ({{ route('admin_regrade') }}).

Entrance practice, for anyone

Anyone with a school's practice address (/entrance-practice on the school's own address) can practise without registering or signing in. They choose the class they are aiming for, then a subject; each attempt draws its questions at random, in a new order, is marked immediately with the answers shown, and is never saved ({{ route('entrance_practice') }}, {{ route('entrance_practice_take') }}).

For each class and subject, an administrator with {{ perm('entrance.practice.manage') }} chooses where the questions come from, on Practice Tests in the entrance workspace ({{ route('admin_practice_tests') }}, {{ route('admin_practice_tests_save') }}). The choice is stored in {{ table('entrance_practice_settings') }}:

SourceWhat is served
Last session's examination (the default)The paper of the most recent earlier session that had one for that class and subject. Works with no setup. If there is none, that subject shows as not available yet.
Custom questionsA bank the school set up for practice, with a chosen number of questions per attempt.

The live exam is protected. A bank used by the current session's configurations is never offered as practice, either as "last session's" or as a custom bank (the save is refused with an explanation). Otherwise practising could reveal the questions of an examination not yet sat. The logic is entrance_practice_paper in {{ file('core/entrance.py') }}.

Things worth knowing

  • The candidate flow keeps a few legacy anonymous-paper URLs (/exam, /answer, /submit, /result) that also serve the candidate flow; they check the candidate id in the session, so one candidate can never reach another's attempt.
  • An attempt's questions are frozen, so editing or deleting a bank question never changes an exam in progress or a past result.
  • Candidate photographs are visible to staff and to that candidate only ({{ file('core/upload_access.py') }}).
