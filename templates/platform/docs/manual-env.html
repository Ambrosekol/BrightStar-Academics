Every setting the platform reads, what it does, its default, and what goes wrong when it is wrong. The main list below is drawn straight from the console's own register of settings ({{ file('control_plane/settings_registry.py') }}), so it always says exactly what the console's Settings page ({{ route('platform_settings') }}) says. The few settings the console does not manage are described by hand after it.

Where a setting comes from, and why a change "does nothing"

A value is looked for in this order, and the first one found wins:

  1. The console's shared settings (stored in the registry, {{ file('control_plane/shared_settings.py') }}). Settings marked shared below, once edited in the console, reach every server within about 10 seconds and override the same name in .env.
  2. The server's real environment (systemd Environment=, Docker -e, the shell).
  3. .env in the project folder (read at start; never overrides the real environment).
  4. The default.

I changed a setting and nothing happened

You see
A value was edited in .env (or the service file), but the application still behaves the old way.
Why

One of: the setting needs a restart (marked restart below); the same name is set in the real environment, which beats .env; or the console's shared settings hold a value for it, which beats both.

Fix
  1. Open the setting in the console ({{ route('platform_settings') }}): it shows the value in use, where it comes from, and which server you are talking to.
  2. If a shared value is set there, edit or remove it there (removing it puts back what the server started with).
  3. Settings marked restart: restart the application on every server.
  4. Check the real environment: sudo systemctl show brightstars -p Environment.
Check
The console shows the new value as in use.

Servers disagree about a setting

You see
A behaviour differs depending on which server handled the request.
Why

Per-server settings (database URLs, the secret, the delivery key, file paths, the proxy layout, pool sizes, and anything needing a restart) live in each server's own environment and must be set the same on every one.

Fix

Keep one environment file for all servers (deployed the same way as the code), and set the per-server settings there. Shared settings are better edited in the console.

Check
The console's Settings page shows the same values on each server.

Settings set only in the server's environment

These are not on the console's Settings page; set them in .env or the service's environment, the same on every server, and restart.

BRIGHTSTARS_STORAGE_BACKEND

Default
local
What it does

Where schools' files are kept: local (a folder per school under BRIGHTSTARS_TENANTS_DIR) or s3 (an S3-compatible bucket, {{ file('core/object_store.py') }}).

If wrong

Any other value stops the application starting. With local on several servers, files saved on one are missing on the others. Switching an existing deployment does not move files: copy tenants/<code>/uploads, data and numbering.json into the bucket first.

BRIGHTSTARS_S3_BUCKET, BRIGHTSTARS_S3_ACCESS_KEY_ID, BRIGHTSTARS_S3_SECRET_ACCESS_KEY, BRIGHTSTARS_S3_ENDPOINT_URL, BRIGHTSTARS_S3_REGION, BRIGHTSTARS_S3_PREFIX

Default
bucket and keys required with s3; endpoint unset (real AWS); region auto; no prefix
What it does

The bucket and credentials for s3 storage. The endpoint is needed for any provider that is not AWS (Cloudflare R2, Backblaze B2, DigitalOcean Spaces, MinIO). A prefix namespaces every school's files, so one bucket can be shared with other uses.

If wrong

A missing bucket or key stops the start-up with "… is not set. Required when BRIGHTSTARS_STORAGE_BACKEND=s3." Wrong keys, region or endpoint: every picture is broken and the log says "Could not read uploads/… from object storage".

BRIGHTSTARS_PG_MAINTENANCE_DB

Default
postgres
What it does

The database CREATE DATABASE connects through when the registry or a new school's database does not exist yet.

If wrong

Creating a school (or init) fails with "database "postgres" does not exist" on providers that have no such database (Aiven's is defaultdb).

BRIGHTSTARS_MAX_DATA_UPLOAD_BYTES

Default
2097152 (2 MB)
What it does

The largest file a bulk import (CSV or Excel) may be.

If wrong

Too low refuses a school's large class list ("That file is larger than the … limit"); split it, or raise this.

BRIGHTSTARS_UPLOAD_CACHE_BYTES

Default
67108864 (64 MB)
What it does

How much uploaded-file content each worker keeps in memory, so a picture asked for again skips the bucket ({{ file('core/storage.py') }}). 0 turns it off.

If wrong

Too high on a small server uses memory each worker needs; too low sends every picture request to the bucket.

BRIGHTSTARS_SERVER_NAME

Default
the machine's host name
What it does

The name the console's Settings page shows for this server, so you know which one you are looking at.

If wrong

Nothing breaks; two servers with the same name are just harder to tell apart.
