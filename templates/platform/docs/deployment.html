This page is a checklist for standing the platform up for real. Read {{ page('architecture', 'Architecture') }} first; the sections on the address and on the launch id explain why several of these steps exist.

The built-in server that python app.py starts (app.run, no debug) is for development and small trials. For production run the application under a proper WSGI server behind a reverse proxy, as below.

What you are deploying

Browser→TLS-terminating reverse proxy
nginx, Caddy, a load balancer→WSGI server
several worker processes→PostgreSQL
registry + one database per school

Plus a school's files, on disk that every worker sees (BRIGHTSTARS_TENANTS_DIR) or in an S3-compatible bucket (BRIGHTSTARS_STORAGE_BACKEND=s3) — see "5. Files" below.

1. Names and certificates

  • The platform address, for operators, the console, the marketing page and these docs: for example platform.brightstars.com. Put it in BRIGHTSTARS_PLATFORM_HOSTS. Keep the company's public website (brightstars.com) on separate hosting; the platform serves only /platform, /marketing and /docs here.
  • The portal domain, under which every school is issued an address: for example schools.brightstars.com, so a school called alpha is at alpha.schools.brightstars.com. Set BRIGHTSTARS_PORTAL_DOMAIN to it and create a wildcard DNS record *.schools.brightstars.com pointing at the proxy.
  • Certificates. A wildcard certificate for the portal domain, one for the platform address, and one for each school's own domain that is added later (Let's Encrypt with the DNS challenge handles the wildcard; a proxy like Caddy can issue per-domain certificates on demand).
  • A school's own domain: the school adds one CNAME (portal.theirschool.example. CNAME alpha.schools.brightstars.com.); you register the hostname in the console.

The proxy must pass the original Host header through unchanged. The Host header is what selects the school. A proxy that rewrites it makes every request "address not found" or, worse, the wrong school.

2. PostgreSQL

  • PostgreSQL 14 or newer (tested on 18). One server can hold the registry and every school's database.
  • A role that can CREATE DATABASE. Schools' databases are created on demand. A separate, less privileged role for schools is possible with BRIGHTSTARS_SCHOOL_DB_TEMPLATE when the databases are created elsewhere.
  • Creating a database that does not exist yet needs a connection to one that already does, first (CREATE DATABASE cannot run inside a transaction). A stock install always has one called postgres, the default; a managed provider that does not ship one under that name (Aiven's default database is defaultdb, for instance) needs BRIGHTSTARS_PG_MAINTENANCE_DB set to whichever one is guaranteed to exist. This only matters the first time — the registry's own database and an already-created school's database are tried directly first.
  • Connections multiply. Each school has its own connection pool, so total connections are roughly schools × pool size × workers. Size max_connections accordingly, or put a pooler in front. With PgBouncer in transaction mode use a database per school, not a schema per school.
  • Back up the registry and every school's database. Restoring one school never touches another.

3. Environment

Everything is read from environment variables (loaded from .env if present; a real environment variable always wins). Minimum for production:

BRIGHTSTARS_ENV=production
BRIGHTSTARS_SECRET=<64 hex characters from secrets.token_hex(32)>
BRIGHTSTARS_PLATFORM_DB=postgresql+psycopg://brightstars:...@db-host:5432/brightstars_platform
BRIGHTSTARS_PLATFORM_HOSTS=platform.brightstars.com
BRIGHTSTARS_PORTAL_DOMAIN=schools.brightstars.com
BRIGHTSTARS_TENANTS_DIR=/var/lib/brightstars/tenants
BRIGHTSTARS_TRUSTED_PROXIES=1
BRIGHTSTARS_DELIVERY_KEY=<a different long random string>
BRIGHTSTARS_CONTACT_EMAIL=hello@brightstars.com
  • BRIGHTSTARS_ENV=production makes session cookies Secure, adds HSTS, and makes the application refuse to start if the secret is under 32 characters.
  • BRIGHTSTARS_TRUSTED_PROXIES is how many reverse proxies you run in front (usually 1). Leave it 0 with none. Too high lets a visitor forge their address in the audit log and dodge the sign-in limits; too low records the proxy's address for everyone. Behind a TLS-terminating proxy it is also what makes links in emails and the "Enter school" redirect use https.
  • BRIGHTSTARS_DELIVERY_KEY encrypts schools' saved mail and WhatsApp secrets independently of the session secret. Set it before any school saves credentials and never change it afterwards. Without it the key derives from BRIGHTSTARS_SECRET, so rotating that secret would make every saved credential unreadable.
  • BRIGHTSTARS_CONTACT_EMAIL is optional: the address the marketing page's buttons write to. Without it the page shows the buttons without a mail link.
  • Optional shared mail and WhatsApp accounts (BRIGHTSTARS_SMTP_*, BRIGHTSTARS_WHATSAPP_*) are the fallback for schools that have set up none. See the full list in the {{ page('reference-config', 'configuration reference') }}.

4. First launch

  1. Install: python -m venv venv, pip install -r requirements.txt, plus a WSGI server (for example gunicorn on Linux, waitress on Windows; neither is in requirements.txt).
  2. python -m control_plane init creates the registry and its tables.
  3. python -m control_plane create-platform-admin <you> makes the super admin (password prompted, at least 10 characters).
  4. python -m control_plane upgrade: brings every school's schema up to date and records a new launch. This is the deploy step when you do not start with python app.py (which does both itself).
  5. Start the WSGI server with several workers, pointing at app:app, for example gunicorn -w 4 -b 127.0.0.1:8000 app:app.
  6. Configure the proxy: TLS, the wildcard, the Host header passed through, X-Forwarded-For and X-Forwarded-Proto set.
  7. Open the platform address, sign in, and create a first real school. Check its sign-in page in a private window.

Why "upgrade" is a deploy step. The launch id (which signs everyone out after a restart) must be written once, before any worker serves a request; workers only read it. If you start workers directly, nothing writes it, and nobody is ever signed out for a restart. Also, a new release may add columns; upgrade adds them to every school's database before requests arrive.

5. Files

A school's uploads, question banks and numbering rules live under one of two storage backends, chosen with BRIGHTSTARS_STORAGE_BACKEND ({{ file('core/storage.py') }}):

  • local (the default): a folder on disk, BRIGHTSTARS_TENANTS_DIR/<code>/. Simplest for one application server with persistent disk. With more than one server this folder must be shared storage visible to every one of them.
  • s3: an S3-compatible object store ({{ file('core/object_store.py') }}) — real AWS S3, or Cloudflare R2, Backblaze B2, DigitalOcean Spaces or MinIO by also setting BRIGHTSTARS_S3_ENDPOINT_URL. Needed whenever the application server's own disk is not persistent (many hosting platforms wipe it on every redeploy or restart) or more than one server must share the same files, with no shared disk to arrange at all. Requires BRIGHTSTARS_S3_BUCKET, BRIGHTSTARS_S3_ACCESS_KEY_ID and BRIGHTSTARS_S3_SECRET_ACCESS_KEY (see the {{ page('reference-config', 'configuration reference') }}), and boto3 installed (already in requirements.txt).

Every stored database value (uploads/<folder>/<file>) is identical under either backend, so switching later does not touch a school's database — it does mean moving existing files into the new backend by hand. A school's generated/ folder (Chrome-rendered result images) is always local under either backend: nothing in it is ever served beyond the one request that made it. Back it up together with the databases; a school is its database plus its files.

On the s3 backend, every uploaded file's bytes are also cached in each worker's own memory once served ({{ file('core/storage.py') }}, BRIGHTSTARS_UPLOAD_CACHE_BYTES, 64 MB by default), so a shared image — a school's logo, shown on every page — is fetched from the bucket once per worker rather than once per request. Both the browser's own cache (a year, immutable — app.py's uploaded_file) and this in-memory one rely on the same fact: an upload's path never changes what it holds, so neither needs to expire on a timer, only make room for newer files once full.

6. Health and monitoring

  • GET /health answers {"status":"ok"} on any address, touches no database and needs no sign-in. Use it for the load balancer.
  • Watch the application log. Failures of best-effort work (a message that could not be sent) are logged with the school and the reason, never raised to the person.
  • Watch for the log warning that the registry could not be reached: rate limits and the launch id then degrade safely (nobody is locked out or signed out), but you want to know.
