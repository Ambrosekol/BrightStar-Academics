Everyone signs in on one page (/login on a school's address); platform admins sign in on the console (/platform/login). A sign-in is a signed cookie, checked on every request by {{ file('core/session_guard.py') }}, which decides whether it is still good. Five things end a sign-in, each with its own message, so the message tells you which one happened:

Message on the sign-in pageWhat ended itRead
The system was restarted, please sign in again.A restart, an upgrade or new-launchbelow
Your password was changed, please sign in again.The account's password changed somewhere elsebelow
You were signed out after a while without using the portal, please sign in again.Idle for BRIGHTSTARS_IDLE_MINUTES (120)below
Your sign-in has run out, please sign in again.Older than BRIGHTSTARS_SESSION_HOURS (12)below
That sign-in was ended by signing out, please sign in again.Someone signed out of this sign-in (perhaps in another tab, or a copy of the cookie)below

Nobody sitting an exam is ever signed out by a restart, the idle limit or the lifetime while their paper is running. A candidate or student mid-paper carries on through a power cut, a lost connection or a server restart, and has 30 minutes more once the paper ends to see the result.

Signed out unexpectedly

"The system was restarted, please sign in again."

You see
Everyone, at once, meets the sign-in page with this message.
Why

The server was started again, an upgrade ran, or someone pressed Sign everyone out ({{ route('platform_settings_new_launch') }}). Each records a new launch id ({{ file('control_plane/launch.py') }}), deliberately ending older sign-ins.

Fix

Nothing is broken; people sign in again. Schedule deploys and restarts outside school hours. If it happens with no restart, check the server is not crash-looping (systemctl status brightstars, uptime) and see {{ page('manual-startup', "It won't start, or a deploy failed") }}.

Check
Sign-ins succeed and stay.

"Your password was changed, please sign in again."

You see
One person is signed out in one browser while still signed in where they changed it.
Why

The account's password changed: by the person, by an administrator resetting it, or by a reset link. Every other browser signed in to that account is signed out (within BRIGHTSTARS_PASSWORD_CHECK_CACHE_SECONDS), on purpose.

Fix

Sign in with the new password. If the person did not change it, treat it as a possible break-in: see {{ page('manual-emergencies', 'Emergency playbooks') }}.

Check
The activity log shows who changed it, and when.

"You were signed out after a while without using the portal"

You see
A person who left a page open returns to the sign-in page with this message.
Why

No page was opened or form sent for BRIGHTSTARS_IDLE_MINUTES (120 by default). The small check an open page makes every 30 seconds does not count, so a tab left open on a shared computer still ends.

Fix

Normal behaviour. If teachers write very long report comments without saving, either ask them to save as they go, or raise BRIGHTSTARS_IDLE_MINUTES (in the console, {{ route('platform_settings') }}). Lowering it suits schools with shared computers.

Check
The new value applies to the next request after a restart.

"Your sign-in has run out, please sign in again."

You see
A person who has been busy all day is asked to sign in again.
Why

A sign-in lasts at most BRIGHTSTARS_SESSION_HOURS (12 by default), however busy, so a forgotten sign-in cannot last for days.

Fix

Normal. Raise BRIGHTSTARS_SESSION_HOURS if a working day is longer than 12 hours.

Check
Sign in again and carry on.

"That sign-in was ended by signing out, please sign in again."

You see
A page in a second tab, or on a second device using a copied cookie, sends the person to sign in.
Why

Signing out records the sign-in as ended in the registry ({{ table('ended_sessions') }}, {{ file('control_plane/ended_sessions.py') }}), so every copy of it stops working.

Fix

Sign in again. If nobody signed out, someone else may have: change the password.

Check
The new sign-in works.

Signed in, then signed out again on the next page

You see
Sign-in "works" but the next click goes back to the sign-in page, with no message.
Why

The sign-in cookie is not coming back. Usual causes: BRIGHTSTARS_ENV=production (cookies marked Secure) while the site is served over plain http; several servers with different BRIGHTSTARS_SECRETs behind one load balancer; or the browser blocks cookies for the site.

Fix
  1. Serve the site over https (and set BRIGHTSTARS_TRUSTED_PROXIES so the application knows it is https).
  2. Give every server the same BRIGHTSTARS_SECRET.
  3. Make sure the proxy passes the Host header unchanged (a sign-in belongs to the school of the address it was made on).
Check
In the browser's developer tools, the session cookie is set after sign-in and sent with the next request.

Cannot sign in

"We could not verify those login details."

You see
We could not verify those login details. Please check your ID/username and password.
Why

The username (or Student ID, Candidate ID, parent email) does not exist, the password is wrong, or the account is inactive. The page deliberately does not say which.

Fix
  • Staff: the School Admin resets it (Settings › Staff, the person's ⋯ menu › reset login). If the School Admin themself is locked out, a platform admin enters the school ({{ route('platform_school_enter') }}) and resets it, or creates a new administrator on the school's console page.
  • Students: staff reset it from the student's page (a new one-time password). An archived student cannot sign in at all, by design.
  • Parents: staff reset it from the parent's record.
  • Candidates: the entrance workspace resets candidate credentials.
  • Anyone with a recovery email can use "Forgot password" on the sign-in page.
Check
The person signs in with the new one-time password and is asked to choose their own.

"Too many sign-in attempts. Please wait a few minutes and try again."

You see
Too many sign-in attempts. Please wait a few minutes and try again. (HTTP 429)
Why

Sign-in is limited, counted in the registry ({{ table('rate_limits') }}) so every server shares the count:

  • 8 tries in 5 minutes for one address and one username;
  • 40 wrong passwords in 15 minutes from one address, across all usernames;
  • 20 wrong passwords in 15 minutes for one username, from any addresses.

Right passwords never count against the last two, so a computer room signing in from one address is fine unless many people get their passwords wrong.

Fix
  1. Usually: wait 15 minutes.
  2. A whole school locked out at once: almost always the reverse proxy hiding real addresses. Set BRIGHTSTARS_TRUSTED_PROXIES; see {{ page('manual-addresses', 'Addresses, domains and proxies') }}.
  3. To lift every limit right now (for example after fixing the proxy): in the registry database, DELETE FROM rate_limits;. Only hashes are stored, so you cannot pick out one person; clearing all is safe.
  4. If one account keeps tripping it, someone may be guessing its password: check the activity log, and consider changing the password.
Check
The person signs in.

"Crèche and Nursery pupils do not sign in."

You see
Crèche and Nursery pupils do not sign in. A parent can sign in to the parent portal …
Why

Early-years pupils do everything on paper; their parents see fees and report cards ({{ file('core/school_structure.py') }}).

Fix

The parent signs in instead. If the child is actually older, move them to the right class: the sign-in follows their current class.

Check
After moving the class, the student signs in.

"This password reset link is invalid or has expired."

You see
The reset page says the link is invalid or has expired.
Why

A link works once and for 30 minutes. Asking for a newer link cancels the older one.

Fix

Ask for a new link and use the newest email only.

Check
The newest link opens the "choose a new password" form.

"Forgot password" sends nothing

You see
The page says instructions will be sent if the account exists, but no email arrives.
Why

The page always says the same thing (so it never reveals whether an account exists). No email goes out when: the account has no recovery email (students' go to the guardian email on their record), the school has no working mail server and the platform has no shared one, or the message went to spam.

Fix
  1. Check the account has an email: staff on their staff record; parents on their parent record; students the guardian email.
  2. Test the school's mail under Settings › Email & SMS (Send a test). If it fails, see {{ page('manual-messaging', 'Email, SMS, background jobs and alerts') }}.
  3. Otherwise staff reset the password directly (above), which needs no email.
Check
The test email arrives; the reset email then arrives too.

A new password is refused

You see
One of: "Your new password must be at least 8 characters long." · "That password is one of the first that people try." · "Your new password needs more than one or two different characters." · "A straight run of letters or numbers is easy to guess." · "Your new password must not contain your username or ID."
Why

New passwords are checked by {{ file('core/passwords.py') }}: at least 8 characters (10 for platform admins), not a common password (password123, school123, nigeria …, even with numbers added at the end), not one character repeated, not a run like 12345678, and not containing the username.

Fix

Choose something longer and personal, for example three unrelated words with a number: mango-river-blue-7.

Check
The password is accepted.

"Access Denied" / "Invalid or missing CSRF token" after pressing a button

You see
A 403 page after submitting a form; the log shows "Invalid or missing CSRF token".
Why

Every form carries a token tied to the sign-in. It no longer matches when the page was opened before the person was signed out (a restart, a timeout), when the form was opened in another account's session, or when cookies are blocked.

Fix

Reload the page (or sign in again) and submit again. If it happens to everyone on every form, the sign-in cookie is not coming back: see Signed in, then signed out again.

Check
The form saves.

Platform admins

"Those platform credentials were not recognised."

You see
Those platform credentials were not recognised. (on /platform/login)
Why

Wrong username or password, or the admin was removed (removal never deletes, it switches access off).

Fix
  • The super admin resets the password on the Team page ({{ route('platform_team_reset') }}) or restores a removed admin.
  • If the super admin is the one locked out: on the server, python -m control_plane create-platform-admin rescue --super creates a second super admin; sign in as it, reset the original's password on the Team page, then remove rescue.
Check
The admin signs in and is asked to set their own password.

"That access link has expired or has already been used."

You see
That access link has expired or has already been used. Start again from the platform console.
Why

Entering a school uses a single-use ticket that lasts two minutes and only works for the school it was made for ({{ file('control_plane/entry.py') }}). A slow page, a second click or a copied link uses or outlives it.

Fix

Press Enter school again on the school's console page and let it redirect.

Check
The school opens, with the operator banner at the top.

"This school has no system role; run upgrade for it first."

You see
Entering a school or adding its first administrator fails with this message.
Why

The school's database was never fully initialised (the School Admin role is created at upgrade).

Fix

python -m control_plane upgrade CODE, then try again.

Check
Entering the school works.

"Exit the current workspace and choose the other workspace from Workspace Home."

You see
A staff member is sent to Workspace Home with this message.
Why

They opened a page of the other workspace (Entrance pages while in School, or the reverse). The two are kept apart on purpose.

Fix

Choose the other workspace on Workspace Home. Staff who only have one workspace go straight into it; giving someone the Entrance workspace is a matter of their role's permissions.

Check
The page opens in the right workspace.
